# 재직증명서 API 명세

Swagger `3. 재직증명서` 태그를 옮긴 것이다. 원본이 항상 우선한다.

| | |
|---|---|
| 출처 | `https://api.dvi-ind.com/hi-yo/v3/api-docs` (Swagger UI `/hi-yo/swagger-ui/index.html`) |
| API 버전 | `DVI 인사시스템 API` v1 |
| 확인일 | 2026-08-28 |
| 서버 | `https://api.dvi-ind.com/hi-yo` (개발) |

**S-401이 이 태그 전부를 쓴다.** 경로가 넷뿐이다.

> **승인 절차가 없다.** 본인이 누르면 그 자리에서 발급된다. 결재 흐름이 없는 유일한 신청이다.

> **삭제·취소가 없다.** `DELETE`는 `405`다 (관리팀 권한으로도 마찬가지).
> 의도된 설계이며 발급 이력을 남긴다 (`docs/00_문서_인덱스.md` — S-401 확정 결정).

---

## 1. 공통

### 인증 · CORS

급여와 같다. `docs/API_급여.md` 1장을 본다.

### 응답 형식

**`GET /certificates`만 봉투**(`content`/`totalElements`)로 온다. `page`는 0부터,
`size`는 서버가 100에서 자른다 (`docs/API_직원.md` 1장).

### 오류

`docs/API_급여.md`와 같은 모양이다.

- `POST /certificates`는 **`201`**을 준다. Swagger에는 `200`으로 선언돼 있다 (앱 동작에는 영향 없음)
- 값 검증 실패는 **`400`** `"요청 값이 올바르지 않습니다."` — 업무 규칙 위반(`422`)과 다른 코드다

## 2. 엔드포인트

| 메서드 | 경로 | 권한 | 용도 |
|---|---|---|---|
| GET | `/certificates` | 본인 | 내 발급 이력 |
| POST | `/certificates` | 본인 | **즉시 발급 — 승인 절차 없음** |
| GET | `/certificates/{id}` | 본인 (스펙상) | 단건 |
| GET | `/certificates/{id}/pdf` | 본인 (스펙상) | PDF 파일 바이트 |

### 발급과 내려받기를 왜 나눴는가

스펙이 직접 적고 있다 —

> "한 번 발급한 증명서를 몇 번을 내려받아도 같은 문서여야 하기 때문이다.
> 내려받기가 발급을 겸하면 새로고침할 때마다 새 문서번호가 찍힌다."

**앱도 이 구분을 지킨다.** 목록에서 이미 발급한 건을 눌러 다시 받을 때 `POST`를 부르지 않는다.

## 3. 스키마

### `CertificateIssueRequest`

`purpose` `submitTo` — **둘 다 선택이고 자유 입력**이다.

스펙 — "용도와 제출처는 본인이 자유 입력한다(요구사항정의서 4).
승인 절차가 없으므로 이 둘 외에 받을 것이 없다."

앱은 최대 100자로 막는다 (`docs/00_문서_인덱스.md` — S-401 확정 결정).

### `CertificateResponse`

**출력에 필요한 값이 모두 들어 있다.**

| 묶음 | 필드 |
|---|---|
| 문서 | `id` `docNo` `issuedAt` `purpose` `submitTo` |
| 사람 | `employeeName` `nationality` `residentNoMasked` `departmentName` `jobGrade` `address` |
| 재직 | `hireDate` `tenureMonths` `tenureText` |
| 회사 | `companyName` `companyAddress` `representative` |

- **`employeeName`은 발급 시점의 정식 성명이다.** 외국인은 여권상 풀네임이 들어간다
  (`EmployeeResponse.legalName`과 같은 값)
- **`tenureText`를 서버가 만든다.** 앱에서 재직기간을 계산하지 않는다
- **`residentNoMasked`는 서버가 마스킹한다.** 앱이 원본을 받아 가리는 일이 없다

> **앱은 `residentNoMasked`와 `address`를 화면에 그리지 않는다.** 응답에 들어 있지만
> PDF 출력용이지 조회 화면에 필요한 값이 아니다. 어깨너머로 보이는 자리에 둘 이유가 없다.

## 4. 앱 관점 정리

- **PDF는 파일 바이트로 온다.** 인증이 헤더 방식이라 브라우저로 URL을 여는 방식은 실제
  인증에서 못 쓴다. `expo-file-system` + `expo-sharing`으로 받는다
- 증명서에는 주민번호와 현주소가 들어간다. **캐시 디렉터리에 받고 공유 시트가 닫히면 지운다**
- 발급 이력은 계속 쌓인다. 목록은 `더 보기`로 이어 붙인다
- 재직중이 아니면 **메뉴 자체를 노출하지 않는다** (명세서 S-401)

## 5. 미확정 — 확인이 필요한 것

### 1. 단건·PDF 권한 — 구멍이 아니었다 (2026-08-31 서버 답변으로 해소)

2026-08-26에 아래 결과를 보고 **권한 검증이 없다고 적어 두었다. 틀린 진단이었다.**

| 요청 | 당시 결과 |
|---|---|
| `GET /certificates/1` — 다른 직원 | `200` |
| `GET /certificates/1/pdf` — 다른 직원 | `200` |
| `GET /certificates/1/pdf` — **인증 헤더 없음** | `200` |
| `GET /certificates` (목록) — 다른 직원 | `200`, `totalElements=0` |

**원인은 스텁 인증이었다.** 서버 답변 —

> 스텁 기본 사용자가 관리팀이었습니다. `STUB_USER=employee:1`이고 그 계정이 `ADMIN`이라,
> 헤더 없이 부르면 관리팀으로 로그인된 상태가 됩니다. `canAccess()`는 `isAdmin() || 본인`이니
> 전부 통과합니다. **"인증 헤더 없음 → 200"이 그 증거입니다** — 진짜로 인증이 없었다면
> 401이 났어야 합니다.

oauth 모드에서는 스텁 필터가 등록되지 않아 재현되지 않는다 (서버가 2026-08-31에 실호출로 확인).
토큰 없음·형식이 틀린 토큰·`X-Debug-Employee-No` 헤더 전부 `401`이고,
`/actuator/health`만 의도적으로 열려 있다.

**"헤더가 없는데 200"을 인증 부재로 읽은 것이 실수다.** 스텁 인증에는 기본 사용자가 있고,
그 사용자가 관리팀이면 권한 검사를 통과한다. 다음에 같은 모양을 만나면 기본 사용자부터 본다.

### 2. 주민번호 마스킹 형태가 문서마다 다르다

`CLAUDE.md` 2장은 `901231-1******`(뒤 1자리 노출), 증명서 양식은 `951106-*******`(뒤 전부 가림)이다.
서버 `residentNoMasked`가 어느 쪽인지 **확인하지 못했다** — 주민번호가 등록된 직원이 없어
값이 `null`로 오고 PDF에도 그 줄이 없다.

출력물과 화면이 다른 규칙을 쓰는 것이라면 그렇게 적어두어야 한다.

### 3. 출력 문서 서식

명세서가 "별도 문서로 관리한다"고 넘겼고 리포에 없다. 지금은 서버가 만드는 PDF를 그대로 받는다.
