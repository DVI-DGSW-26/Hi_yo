## 앱 개발을 막고 있는 것 (우선순위)

1. **인증 방식** — **사내 OAuth로 정해졌다** (bearer JWT). 2026-08-31 오전에 서버가 켰고,
   그 순간부터 두 앱이 전부 `401`이 됐다.

   **그런데 프런트는 아직 붙을 수 없다.** `hi-yo`가 confidential client라 secret이 필요하고,
   등록된 redirect URI도 서버용이다. 프런트가 붙으려면 public client를 새로 등록해야 하는데
   그건 SSO 쪽 terraform 작업이다.

   **되돌리지 않고 로그인을 붙였다** (2026-08-31). 서버가 `AUTH_MODE=local`로 되돌려 주겠다고
   했으나, 백엔드가 「HRM 로그인 연동 안내」를 주면서 붙일 수 있게 됐다.
   관리팀 화면은 `apps/admin/src/lib/auth.ts`에 들어 있다.

   **모바일에도 붙였다** (`apps/mobile/src/lib/auth.ts`). 웹과 흐름은 같고 다른 것은 둘이다 —
   돌아오는 곳이 웹 주소가 아니라 앱 딥링크이고, 토큰을 `expo-secure-store`에 둔다.
   **라이브러리를 더하지 않았다** — `expo-linking`과 `expo-secure-store`가 이미 있어서
   시스템 브라우저를 여는 방식으로 만들었다. 앱 안에서 열리는 로그인 시트가 필요하면
   `expo-web-browser`를 제안한다.

   **아직 끝까지 돌리지 못했다.** 서버에 등록돼야 하는 것 —
   관리팀 콜백 `http://localhost:5173/auth/callback`, 모바일 콜백(아래), 그리고
   테스트 계정의 Keycloak 아이디다.

   **모바일 콜백 주소는 빌드마다 다르다.** 운영 빌드는 `app.json`의 `scheme`을 따라
   `hr://auth/callback`이지만, 개발 빌드는 앞이 달라진다. 그래서 개발 빌드의 로그인 화면이
   실제 값을 화면에 찍는다 — 기기에서 읽어 서버에 알린다.

   **서버가 커스텀 스킴으로 리다이렉트해 주는지 확인되지 않았다.** 백엔드 안내는 웹 주소만
   예로 들고 있다. 안 되면 중간에 웹 페이지를 한 번 거치는 방식으로 바꿔야 한다.

   붙일 때 지킬 것 둘 —
   - **`GET /auth/me`로 권한을 받는다.** 로그인 직후 부른다.
     `{ employeeId, employeeNo, name, role, admin }`
   - **토큰의 `resource_access`를 직접 읽지 않는다.** 병행 기간에는 앱 DB의 권한이 이겨서,
     토큰은 `user`인데 실제로는 관리팀인 사람이 있다. 토큰을 보고 화면을 그리면 관리 메뉴가 사라진다
2. **전자서명 구현 방식** — 거의 풀렸다 (2026-08-31 서버 답변).
   `signatureImage`는 **base64 문자열**이고(URL 아님), `CLICK`일 때는 **보내지 않아도 된다.**

   남은 것은 **크기 상한 하나뿐이고, 실측값은 넘겼다** (2026-08-31).
   보통 서명 23KB · 빽빽한 낙서 54KB이고 획을 더 늘려도 55KB 근처에서 멈춘다.
   서버가 예상한 "50KB 안쪽"이 맞았다. `base64` 기준 **128KB**를 상한으로 제안했다.
   자세한 표는 `API_신청결재.md` 8장에 있다.

   **캔버스 백킹스토어를 DPR 2로 고정한다.** 기기 값을 그대로 쓰면 DPR 3에서 한 장에
   200~370KB가 된다
3. **화면 상세 스펙** — 명세서 8장 5번. S-101/302/501/502/601은 아예 없다.
   S-503은 "상세 스펙 있음"으로 분류돼 있으나 실제로는 서술 3문장이고 필드표가 없다.
   **다만 S-503은 API가 명세서보다 자세해서 막혀 있지 않다** (아래 「S-503 교체 동의 화면」)
4. **Pretendard 폰트 파일** — `fontFamily`는 정해졌으나 폰트가 없어 시스템 폰트로 떨어진다. `expo-font` + `.otf` 필요
5. **`DESIGN_RULES.md` 6장 문구 규칙** — `DESIGN_SYSTEM.md` 7장이 요약본만 담고 있다

해소됨: 디자인 토큰 (2026-08-24 `DESIGN_SYSTEM.md` 반영)

### S-301 잔여연차 초과 신청 차단 (2026-08-24 확정)

명세서 검증 규칙은 "신청 버튼 비활성화 **또는** 제출 시 오류 반환"으로 두 방법을 허용한다.
**제출 시 오류 반환**으로 간다.

- 버튼은 항상 눌린다. 누르면 인라인 에러로 이유를 알린다
- `Button`에 `disabled`를 추가하지 않는다 (DESIGN_SYSTEM.md 5장)
- 초과 판정은 서버가 준 잔여일수로 한다. 앱에서 연차를 합산하지 않는다

### S-401 용도·제출처는 자유 입력 (2026-08-26 확정)

`DESIGN_SYSTEM.md` 1장 그린 예산표가 재직증명서의 그린 1곳을 "선택된 용도 칩"으로 적고 있었다.
칩이라면 선택지 목록이 있어야 하는데 명세서에도 API에도 없다. 둘 다 **자유 입력**이라고 적혀 있다.

- 명세서 S-401 — 용도·제출처 자유 입력, 둘 다 필수 아님
- `CertificateIssueRequest` — `purpose` / `submitTo` 자유 문자열, 최대 100자

명세서·API를 따라 `TextField`를 신설했다. 그린 예산표의 재직증명서 행을 고쳤다
(1곳 = `발급받기` 버튼, 2곳 없음).

### S-401 발급 이력은 지우지 않는다 (2026-08-26 확정)

재직증명서에는 삭제·취소 API가 없다. `GET /certificates`, `POST /certificates`,
`GET /{id}`, `GET /{id}/pdf` 넷뿐이고 `DELETE`는 405를 준다 (관리팀 권한으로도 마찬가지).

**의도된 설계다. 발급 이력을 남겨야 한다.**

- 화면에 삭제·취소 버튼을 만들지 않는다
- 잘못 발급했으면 다시 발급한다. 이전 건은 이력에 남는다
- 개발 서버에 남겨뒀던 테스트 발급 2건은 **없어졌다.** 시드가 다시 심어졌다
  (2026-08-28. 아래 「개발 서버 데이터가 통째로 바뀌었다」)

### S-401 PDF 처리 (2026-08-26 확정)

`GET /certificates/{id}/pdf`가 파일 바이트를 준다. 인증이 헤더 방식이라 브라우저로 URL을 여는

### S-503 교체 동의 화면을 만든다 (2026-08-28 확정)

명세서 흐름은 "교체 신청 → **상대방 동의** 대기(24시간) → 확정"이고, 알림 트리거표(6장)도
교체 요청을 **상대방에게 앱 푸시**로 보낸다고 적고 있다. 그런데 **동의를 누를 화면이
화면 인벤토리 25개 어디에도 없다.** 푸시를 받고 열 데가 없는 상태다.

**S-503 안에 "나에게 온 교체 요청" 영역을 만든다.** 별도 화면번호를 새로 파지 않는다 —
같은 명단·같은 스케줄을 보는 화면이고, 본인용 화면을 늘리면 하단 메뉴가 같이 늘어난다.

**API는 전부 있다 (2026-08-28 Swagger·실호출 확인).** 명세서보다 API가 더 자세하다.

| 경로 | 쓰는 곳 |
|---|---|
| `GET /duty/schedules/{employeeId}` | 내 당직 일정 (`from`·`to` 필수) |
| `GET /duty/swaps/inbox` | **나에게 온 교체 요청 — 마감 임박 순** |
| `POST /duty/swaps/{swapId}/decision` | 동의·거절 (`agreed` 필수, `comment` 선택) |
| `POST /duty/schedules/{scheduleId}/swaps` | 교체 신청 (`targetId` 필수, `reason` 선택) |
| `GET /duty/swaps/sent` | 내가 보낸 요청 |
| `DELETE /duty/swaps/{swapId}` | 신청 취소 |
| `GET /duty/rosters` | 명단·슬롯 정의 |

명세서에 없던 것이 API에서 풀렸다.

- **교체 상대방은 그 명단 안의 사람만 된다.** `POST /duty/schedules/{scheduleId}/swaps`가
  "본인 당직만, 명단 안의 사람에게만 보낼 수 있다"고 적고 있고 서버가 검증한다.
  후보 목록은 `GET /duty/rosters/{rosterId}/members`다. **앱에서 후보를 추려내지 않는다**
- **`EXPIRED`와 `REJECTED`를 구분해 보여줘야 한다.** `DutySwapResponse`가 명시적으로 요구한다 —
  "`EXPIRED`는 거절과 다르다. 상대방이 못 본 것이므로 다시 요청하거나 다른 사람에게 부탁할 수 있다"
- `DutyScheduleResponse.swapPending`으로 교체 요청이 걸린 배정을 표시할 수 있다
- 경비교대는 `useSlot: true`에 `slotCode`(`LUNCH` 11:30~12:00 / `DINNER` 16:30~17:00)로 온다.
  같은 날짜에 두 건이 오며 각각 별개 배정이다. 하루 단위 일괄 교체 버튼을 만들지 않는다

**만든 것은 확인과 응답까지다.** 부탁하는 쪽은 만들지 않았다 —
`targetId`를 고를 방법이 없다 (아래 「서버에 알려야 할 것」). 화면 이름이
"확인·교체 신청"이지만 지금 만들 수 있는 절반이 그렇다.

| 만든 것 | 안 만든 것 |
|---|---|
| 내 당직 달력·목록 | 교체 부탁하기 — 후보를 볼 수 없다 |
| 나에게 온 부탁 목록·동의·거절 | 보낸 부탁 취소하기 — 대화상자가 없다 |
| 내가 부탁한 것의 상태 | |

취소(`DELETE /duty/swaps/{id}`)는 되돌릴 수 없는 동작이라 확인 단계가 필요한데
모바일 `src/components`에 대화상자가 없다. 만들기 전에 사람에게 묻는다
(`DESIGN_RULES.md` 1장 3번).

**화면을 열어도 지금은 빈 상태만 보인다.** 명단 3개의 `memberCount`가 전부 `0`이라
배정도 교체 요청도 없다 (2026-08-28 실호출). 확인하려면 A-504로 명단에 사람을 넣어야 한다.

### A-504 당직 명단·스케줄 관리 (2026-08-28 만듦)

명세서는 A-504를 화면 인벤토리에만 두고 상세 스펙을 주지 않는다. 데이터 모델(1.4)과 API가
확정돼 있어 명세서 3장의 "그 외 화면은 데이터 모델 및 화면 인벤토리를 기준으로 준용한다"를
따랐다. 보험 요율을 올린 것과 같은 기준이다.

명단은 **서버가 정의해 준다.** 만들거나 지우는 API가 없다 — 화면도 만들지 않는다.
개발 서버에 셋이 있고 명세서 S-503의 세 명단과 정확히 맞는다.

| 명단 | 순환 | 자동 편성 | 슬롯 |
|---|---|---|---|
| 당직(일직) `DAY_DUTY` | `BIWEEKLY` (14일마다) | 가능 | 없음. 08:00~17:00 |
| 평일연장 `WEEKDAY_OVERTIME` | `ON_DEMAND` (수시) | **불가** | 없음 |
| 경비교대 `GUARD_SHIFT` | `DAILY` (매일) | 가능 | **중식 11:30~12:00 · 석식 16:30~17:00** |

화면에서 정한 것.

- **순번을 화면에서 다시 매기지 않는다.** 서버가 준 순서가 곧 도는 순서다.
  가나다순 정렬이 아니고, 관리팀이 정한 값 그대로 자동 편성이 돈다
- **자동 편성에 확인 대화상자를 두지 않는다.** 이미 배정된 날짜를 건드리지 않아 몇 번을
  다시 돌려도 안전하다. 되돌릴 수 없는 동작이 아니다 (`DESIGN_ADMIN.md` 6장)
- **연차와 겹친 배정(`conflicts`)은 표 위에 건수와 명단으로 남긴다.** 서버가 겹친 건을
  건너뛰지 않고 그대로 배정한 뒤 알려준다. 다음 순번으로 넘길지 사람을 바꿀지가 확정되지
  않아(서버 스펙 `OPEN-QUESTIONS E-8`) 화면도 대신 고치지 않는다
- **`자동 편성하기`에 `disabled`를 썼다.** 명단이 `autoAssignable: false`거나 대상자가 0명이면
  누를 수 없고 이유를 버튼 옆에 적는다. 사용자가 이 화면에서 고칠 수 없거나 고칠 곳이 따로
  있는 상태이며 서버도 같은 검증을 한다 — `DESIGN_ADMIN.md` 1장의 두 조건을 지켰다
- **배정 상태 문구는 API를 따랐다.** 명세서 1.4는 `예정/확정/완료`인데 API는
  `PLANNED/DONE/SWAPPED`를 준다. `확정`에 해당하는 값이 없고 `교체됨`이 명세서에 없다
- 상태를 그린으로 칠하지 않았다. 셋 중 어느 것도 A-601의 `확정`처럼 되돌릴 수 없는
  이정표가 아니라 그냥 시점이다. 이 화면의 그린은 `자동 편성하기` 하나다

**대상자를 아직 넣지 않았다.** 직원 103명이 실제 명단으로 보여 임의로 넣지 않았다.
명단 셋 다 `memberCount`가 `0`이고, 그래서 S-503도 열면 빈 상태만 보인다.

### A-503 52시간 근접 알림 현황 (2026-08-28 만듦)

서버가 `GET /attendance/weekly`를 **"52시간 근접 현황 — 관리팀 화면"**이라고 적어 두었다.
화면을 상정하고 만든 엔드포인트라 A-504와 같은 기준(명세서 3장 준용)으로 붙였다.

**단계는 서버가 정한다.** `WeeklyWorkSummaryResponse` 스키마가 직접 그렇게 적고 있다 —
"프런트가 분 단위로 다시 판단하면 서버와 기준이 어긋나므로 단계를 서버가 정합니다."

| `alertLevel` | 화면 문구 | tone |
|---|---|---|
| 0 | `여유 있어요` | neutral |
| 1 (48h) | `48시간을 넘겼어요` | neutral |
| 2 (52h 임박) | `52시간이 코앞이에요` | **error** |
| 3 (초과) | `52시간을 넘겼어요` | **error** |

**서버 설명은 이 단계를 "화면에서 색을 고르는 기준"이라고 하지만 색은 셋뿐이다.**
`DESIGN_ADMIN.md` 7장이 `done`·`error`·`neutral` 말고 새 tone을 만들지 못하게 하고 뱃지도 금지한다.
그래서 **경고(2)와 초과(3)를 같은 빨강**으로 두고 구분은 문구가 한다 — 넘긴 것과 넘길 것 둘 다
관리팀이 지금 손대야 하는 줄이라 같은 무게로 봤다.

그 밖에 정한 것.

- **거르는 것도 서버가 한다.** `onlyAlerted`를 서버에 넘긴다. 앱에서 `alertLevel`로 거르면
  기준이 어긋났을 때 관리팀이 놓치는 사람이 생긴다
- **기본값을 `알림 대상만`으로 둔다.** 주 52시간은 넘기면 회사가 처벌받는다.
  전 직원 표가 아니라 손댈 사람 명단으로 읽혀야 한다
- `remainingMinutes`는 넘겼으면 음수로 온다. `formatMinutes`가 부호를 붙이고,
  음수인 칸만 `danger` 글자로 둔다. **여기서 다시 계산하지 않는다**
- 조회만 하는 화면이라 primary 버튼이 없다. 그린도 없다 (`DESIGN_ADMIN.md` 7장 —
  조회가 목적인 화면은 1곳 이하가 정상이다)

**근태 기록이 서버에 하나도 없다.** `GET /attendance/weekly`도 `GET /attendance/daily`도
어느 주를 봐도 빈 배열이다 (2026-08-28 실호출). 세콤 수집(`POST /attendance/collect`)이
아직 안 돌았거나 원본이 없는 것으로 보인다. **그래서 값이 찬 표는 아직 못 봤다.**

날짜 표기는 `apps/admin/src/lib/datetime.ts`에 모았다. 관리팀 화면에는 날짜 라이브러리가 없고
이것 때문에 더하지 않았다 — `Intl`과 `Date.UTC`로 되는 범위다. A-504가 각자 갖고 있던
`todayInKst`·`weekdayText`도 같이 옮겼다.

`apps/admin` `/holidays`. 화면번호가 없다 — 명세서 화면 인벤토리 25개에 없는 화면이다.

화면에서 정한 것.

  손이 미끄러진 것이거나 대체공휴일을 같이 넣어야 하는 날이다
- **고를 수 있는 연도는 올해와 내년뿐이다.** 등록된 연도를 서버에서 알아낼 방법이 없다 —
  `/years` 경로가 없고 `year`를 비우면 전체가 오지 않는다 (`API_연차.md` 9장).
  지난 해는 계산이 이미 끝났고 지워도 되돌아가지 않아 목록에 두지 않았다
- **삭제에 `danger` 버튼과 확인 대화상자를 썼다.** 지우면 이후 계산에서 그날이 근무일이 되고,
  이미 그 날짜로 계산된 연차는 되돌아가지 않는다 (`DESIGN_ADMIN.md` 5·6장)
- 수정 API가 없다. 고치는 화면을 만들지 않았다 — 지우고 다시 넣는다

**`holidayType`이 풀렸다.** `PUBLIC`·`COMPANY` 두 값이다 (`API_연차.md` 9장).
다만 **구분에 따라 연차 차감이 달라지는지는 모른다** — 회사 지정 휴무일을 넣기 전에 확인한다.

### A-304 단체연차 (2026-08-31 만듦)

화면에서 정한 것.

- **등록 대화상자의 날짜 기본값은 오늘이다.** 이 화면을 여는 가장 흔한 경우가 그것이다.
  여름휴가처럼 미리 잡는 날은 고쳐서 넣는다
- **잔여가 모자란 사람을 화면이 처리하지 않는다.** `insufficient` 명단을 표 위에 건수와 함께
  남기고 끝낸다 — 급여의 `skipped`, 자동 편성의 `conflicts`와 같은 자리다.
  무급 전환이냐 마이너스냐는 아래 미확정에 걸려 있다
- **`차감 완료`를 그린으로 뒀다.** A-601의 `확정`과 같은 되돌릴 수 없는 이정표다.
  이 화면의 그린은 등록 버튼과 이것 둘이다 (`DESIGN_ADMIN.md` 7장)
- 삭제 API가 없어 삭제 버튼을 만들지 않았다

**미확정 — 부족분 처리가 명세서와 어긋난다.** 명세서 5장 예외 2번은 "잔여분까지는 연차 차감,
부족분은 무급 처리로 자동 전환"인데 **서버는 자동 전환을 하지 않고 명단으로 돌려준다.**
서버 스펙이 "무급 전환이나 마이너스 처리는 시스템이 정할 문제가 아니다"라고 못박고 있어
**화면도 대신 정하지 않았다.** 어느 쪽이 맞는지 인사팀이 정해야 한다.

**실제로 차감해 본 적이 없다.** 등록·차감 둘 다 되돌릴 수 없고 개발 서버에 지우는 경로가
없어 화면 확인은 빈 목록까지만 했다 (2026-08-31). 연차 발생이 0건이라 지금 차감을 돌리면
**103명 전원이 `insufficient`로 나올 것으로 보인다.**

### ~~재직증명서 단건·PDF에 권한 검증이 없다~~ — 구멍이 아니었다 (2026-08-31 해소)

**2026-08-26에 아래 결과를 보고 권한 검증이 없다고 적었다. 틀린 진단이었다.**

원인은 스텁 인증이다 — `STUB_USER=employee:1`이 `ADMIN`이라, 헤더 없이 부르면 관리팀으로
로그인된 상태가 된다. `canAccess()`가 `isAdmin() || 본인`이라 전부 통과한다.
**"인증 헤더 없음 → 200"이 오히려 그 증거다** — 진짜로 인증이 없었다면 401이 났어야 한다.
oauth 모드에서는 재현되지 않는다 (서버가 같은 날 실호출로 확인).

자세한 것은 `API_재직증명서.md` 5장 1번에 있다. 아래는 당시 관측이다.

| 요청 | 결과 |
|---|---|
| `GET /certificates/1` — 발급자 본인 (`employee:2`) | `200` |
| `GET /certificates/1` — **다른 직원** (`employee:3`) | `200` — 남의 증명서가 그대로 나온다 |
| `GET /certificates/1/pdf` — **다른 직원** (`employee:3`) | `200` — PDF까지 받아진다 |
| `GET /certificates/1/pdf` — **인증 헤더 없음** | `200` — 그대로 받아진다 |
| `GET /certificates` (목록) — 다른 직원 | `200`, `totalElements=0` — 목록은 격리돼 있다 |

증명서에는 성명·부서·재직기간이 들어가고, 주민등록번호와 현주소도 등록되면 들어간다.
id가 `1`부터 순번이라 훑기도 쉽다. **목록만 막고 단건·PDF가 열려 있다.**

앱은 본인 id로만 호출하므로 이 구멍을 쓰지 않는다. 그러나 클라이언트가 막을 수 있는 문제가 아니다.
서버에서 요청자와 증명서 소유자를 대조해야 한다.

**위 표의 증명서 `id=1`은 지금 없다** — 시드가 다시 심어졌다 (2026-08-28). 고쳐졌는지는 확인하지
못했다. 구멍이 남아 있는지 다시 보려면 증명서를 새로 발급하고 다른 직원 id로 불러봐야 한다.

### 교체 상대 후보를 본인이 볼 수 없다 (2026-08-28 확인)

**S-503의 교체 신청 절반을 막고 있다.**

`POST /duty/schedules/{scheduleId}/swaps`는 `targetId`가 필수다. 그런데 **일반 직원은
누구에게 부탁할 수 있는지 알아낼 방법이 없다.** 후보를 담은 두 경로가 모두 막혀 있다.

| 요청 | `employee:1` (관리팀) | `employee:2` · `employee:3` |
|---|---|---|
| `GET /duty/rosters/{id}/members` — 명단 대상자 | `200` | **`403`** |
| `GET /duty/schedules` — 당직표 전체 | `200` | **`403`** |
| `GET /duty/rosters` — 명단 정의 | `200` | `200` |
| `GET /duty/swaps/inbox` · `/sent` | `200` | `200` |
| `GET /duty/schedules/{내 id}` | `200` | `200` |

Swagger에는 `GET /duty/rosters/{id}/members`에 **`관리팀만` 표시가 없다.** 같은 태그의
`POST`·`DELETE`·`PATCH`에는 붙어 있어서 조회는 열려 있는 것으로 읽힌다. 실제로는 막혀 있다.
스펙과 동작 중 어느 쪽이 의도인지 정해야 한다.

- 의도가 "본인도 명단을 본다"면 → `GET /duty/rosters/{id}/members`를 본인에게 열어준다
- 의도가 "명단은 관리팀만 본다"면 → **부탁할 상대를 고를 다른 방법이 필요하다.**
  같은 명단에 속한 사람만 담은 조회를 따로 열거나, `targetId` 없이 명단 전체에 부탁을
  거는 방식이 있어야 한다

그때까지 S-503은 확인과 응답까지만 만들었다. 부탁하는 화면은 만들지 않았다.

**권한이 제대로 걸려 있는 것도 확인했다.** `GET /duty/schedules/{employeeId}`에 다른
직원의 id를 넣으면 `403`이다. 재직증명서 단건·PDF가 열려 있는 것(위)과 대조된다 —
당직 쪽은 요청자와 대상자를 대조하고 있다.

### `PUT /employees/{id}`가 전체 교체라 주민등록번호가 지워진다 (2026-08-26 확인)

**A-102 수정 화면을 만들 수 없는 이유다.**

`PUT /employees/{id}`는 보내지 않은 필드를 지운다. 개발 서버에 실호출해 확인했다.

```
사원001 원본        부서=임원, 직무=사무직
PUT (필수 3개만)    부서=null, 직무=null      ← 생략한 필드가 지워졌다
```

(확인 후 원래 값으로 되돌려 두었다.)

`EmployeeUpdateRequest`에는 `residentNo`가 들어 있다. 그런데 **주민등록번호는 어떤 조회
응답에도 담기지 않는다** — `EmployeeResponse`는 "어떤 경우에도 담지 않는다", `EmployeeDetailResponse`는
"재직증명서 출력 경로에서만 쓰이므로 여기에 담지 않는다"고 스펙에 적혀 있다.
화면이 받을 수 있는 것은 `residentNoRegistered` 불리언뿐이다.

**읽을 수 없는 값을 다시 보낼 방법이 없다.** 그래서 직원 정보를 한 번 수정할 때마다
주민등록번호가 지워진다. 그러면 그 직원은 재직증명서를 발급받지 못한다.

클라이언트가 막을 수 있는 문제가 아니다.

#### 요청 — `PATCH /employees/{id}/resident-no` 를 열어달라 (2026-08-28)

이 리포지토리는 **같은 이유로 PUT에서 빠져나온 엔드포인트를 이미 둘 쓰고 있다.**

| 엔드포인트 | 하는 일 |
|---|---|
| `PATCH /employees/{id}/employee-no` | 사번 부여 |
| `PATCH /employees/{id}/status` | 휴직·복직·퇴사 |

주민등록번호도 같은 모양으로 분리하면 된다. `PUT`을 부분 수정으로 바꾸는 것보다 범위가 좁고,
이미 있는 패턴이라 클라이언트 쪽 변경도 `useAssignEmployeeNo`와 같은 형태 하나 늘리는 것으로 끝난다.

**우회(PUT에 읽은 값을 전부 다시 실어 보내기)가 위태로운 이유.**

계좌정보는 걱정하지 않아도 된다 — `EmployeeUpdateRequest`에 **계좌 필드가 없다.**
`PUT /employees/{id}/bank-account`로 이미 분리돼 있고 스키마 설명도 그렇게 적고 있다
(2026-08-28 Swagger 확인. 2026-08-26자 초안에 "계좌번호가 마스킹 값으로 덮어써진다"고 적었던 것은
틀렸다). 계좌는 이 문제의 사례가 아니라 **이미 올바르게 분리된 선례**다.

남는 문제는 둘이다.

- **`departmentId`·`jobId`를 되돌려 보낼 수 없다.** `EmployeeUpdateRequest`는 id를 받는데
  조회 응답은 `departmentName`·`jobName`만 준다. 이름으로 id를 역매핑해야 하고,
  이름이 겹치거나 부서명이 바뀌면 엉뚱한 부서로 옮겨진다
- **주민번호 하나 넣자고 인적사항 16개 필드를 전부 다시 쓰는 요청을 보내게 된다.**
  그 사이 다른 사람이 수정한 값을 덮어쓴다

`phone`·`email`·`address`가 마스킹돼 오는지는 **확인하지 못했다.** 개발 서버 직원 103명 전원이
이 값들이 `null`이다. 마스킹돼 온다면 위 우회는 연락처까지 망가뜨린다.

그때까지 A-102는 등록·재직상태 변경·사번 부여만 만들었다. 인적사항 수정은 만들지 않았다.
주민등록번호 등록 화면도 이 엔드포인트가 열리기 전까지 만들지 않는다.

### 개발 서버 데이터가 또 통째로 바뀌었다 (2026-08-31)

**인증을 바꾸면서 시드를 다시 심었다** (서버 답변). 개발용 더미 37명을 지우고
**세콤 인사정보 102명 + 관리팀 자료**(연차관리대장·월간근태현황·급여대장)로 다시 만들었다.
지금은 **재직 46명 / 퇴사 56명**이다. `employee:1`이 401이던 것도 그때 id가 새로 매겨졌기 때문이다.

**공휴일은 지우지 않았다.** 재구축 대상은 직원과 그에 딸린 업무 데이터뿐이고,
공휴일·부서·직무·보험요율 같은 마스터는 그대로 뒀다고 한다.
**8/31 00:52에 넣은 설날·추석 6일은 살아 있을 것이다** — 인증이 풀리면
`GET /holidays?year=2026`으로 15건인지 먼저 확인한다.

앞으로 데이터를 건드릴 일이 있으면 먼저 알려주기로 했다.

### 개발 서버 데이터가 통째로 바뀌었다 (2026-08-28 확인)

**시드가 다시 심어졌다. 직원 id가 전부 다른 사람을 가리킨다.** 실호출로 확인했다.

| 확인한 것 | 2026-08-26 | 2026-08-28 |
|---|---|---|
| 직원 수 | 37명 | **103명** (세콤 동기화로 보인다) |
| `employee:1` | 관리팀 | **`401` — 없는 id다** |
| `employee:2` | 일반 직원 | 다른 사람. **퇴사 상태** |
| `employee:3` | 관리팀(결재 2단계) | 다른 사람. **퇴사 상태** |
| 직원 `id=38` | 우리가 만든 `테스트직원` | **다른 사람** |
| 재직증명서 `id=1`, `id=2` | 있음 | **`404`** |
| 급여 기간 | `id=1` 2026년 8월 | **없음** (빈 배열) |

그전에 만들어 둔 테스트 데이터는 남아 있지 않다. **"지우지 않는다"고 적어둔 것이 무의미해졌다** —
지운 것은 우리가 아니고, 서버를 다시 심으면 또 사라진다. 화면 확인용 데이터를 만들 때
그것이 오래 남아 있을 것으로 보고 문서에 적지 않는다.

**Swagger의 스텁 인증 설명도 옛날 것이다.** `employee:1` 관리팀 / `2` 일반 직원 /
`3` 관리팀(결재 2단계)이라고 적혀 있으나 셋 다 맞지 않는다. 서버에 알려야 한다.

지금 쓸 수 있는 id (2026-08-28 확인. **또 바뀔 수 있다**).

| 쓰임 | id | 확인 방법 |
|---|---|---|
| 관리팀 (부서 `관리`) | `58`, `4` | `GET /employees?size=1`이 `200`이면 관리팀, `403`이면 일반 직원 |
| 재직 중인 일반 직원 | `90`(개발), `89`(품질) | `GET /employees/me`의 `employmentStatus`가 `ACTIVE` |

헤더를 아예 비우면 서버의 기본 사용자로 인증된다. 지금은 그 사용자도 관리팀이다.

### 주민등록번호 입력 경로가 화면 스펙에 없다 (2026-08-26, 2026-08-28 갱신)

명세서 A-102의 필드 목록에 주민등록번호가 없다. 그런데 재직증명서에는 들어가야 한다.
지금 화면으로는 등록할 방법이 없고, 개발 서버의 직원 **103명 전원이 미등록 상태**다
(2026-08-28 재확인. 세콤 동기화로 37명에서 늘었다).

**어느 화면에서 입력할지는 정했다** — 관리팀 전용 등록 화면을 신설한다
(「화면 구현 결정」 참고). 서버의 `PATCH /employees/{id}/resident-no`를 기다린다.

아직 정해지지 않은 것 — **누가 입력하는가.** 관리팀 전원인지 특정 담당자인지가 미정이다.
권한 체계(미확정 1번)와 같이 정해져야 한다.

### 그 밖에 확인된 차이

- `POST /certificates`는 **201**을 준다. Swagger에는 200으로 선언돼 있다.
  **201이 맞고 스펙이 틀렸다** — 서버가 문서를 고치기로 했다 (2026-08-31).
- 값 검증 실패는 **400** `"요청 값이 올바르지 않습니다."`다. 업무 규칙 위반(422)과 다른 코드다 —
  앱의 오류 분기(`lib/apiError.ts`)는 이 구분을 그대로 따른다.
