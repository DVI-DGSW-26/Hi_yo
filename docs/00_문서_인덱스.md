## 지금 어디까지 됐나 (2026-09-03)

**「개발 어디까지 됐냐」는 물음에 이 절을 그대로 읽어주면 된다.** 값이 바뀌면 여기를 고친다.

### 만든 것

| | 개수 | 무엇 |
|---|---|---|
| 관리팀 웹 | **화면 14개** | 직원 목록·상세·등록·재직상태 변경·사번 부여 · 직무·부서 조회 · 연차 달력 · 연차 결재(승인·반려) · 연차관리대장 · 단체연차 등록·차감 · 공휴일 등록·삭제 · 근태 현황 · 근태 정리(세콤 수집·판정 실행·보정) · 52시간 · 당직 명단·자동 편성·배정 · 급여 기간 등록·계산 실행·대장·금액 수정·확정·마감 · 보험요율 조회 |
| 모바일 | **영역 6개** | 마이페이지 조회 · 연차 신청(반차·외출·조퇴 시각 포함)·취소 · 재직증명서 신청·PDF · 내 근태와 52시간 · 급여명세서(확정된 달) · 당직 확인과 교체 응답 |

목록에는 **검색·필터**가 붙어 있다 — 직원은 서버 파라미터로, 대장·근태·52시간은 화면에서
거른다(전 직원이 배열로 통째 오는 목록만. `DESIGN_ADMIN.md` 8장).

### 아직 못 본 것

**값이 찬 화면을 한 번도 보지 못했다.** 전 API가 `401`이라 **목 데이터로만** 확인했다.
로그인은 셋 남았고 **둘이 우리 몫**이다 — 이유진·김민준 Keycloak 가입, SSO 팀
`/engineering` 그룹 배정. 서버 몫은 `hr://auth/callback` 등록 하나다.

**모바일은 실기기에서 한 번도 띄우지 못했다.** EAS 개발 빌드가 필요하다.
큰 글꼴은 **스타일 값을 옮긴 페이지에 실제 Pretendard 를 실어** 재고 두 곳을 고쳤다
(아래 「모바일 큰 글꼴 점검」). 기기에서 잰 값이 아니므로 **빌드가 나오면 다시 잰다.**

### 서버를 기다리느라 못 만든 화면 여섯

| 화면 | 무엇이 없어서 | 물어볼 것 |
|---|---|---|
| A-102 인적사항 수정 | 주민번호 전용 경로, `PUT`이 부서·직무를 id로 못 받는 것 | 1 · 2 |
| S-101 계좌 수정 | 무엇이 마스킹돼 오는지 모른다 | 10 |
| S-503 교체 신청 | 같은 명단 조회가 `403` | 3 |
| A-306 연차 발생 등록 | `grantType` 다섯 개의 뜻 | 5 |
| S-302 · A-305 연차촉진 | **조건은 2026-09-02에 확보했다. 경로 셋만 없다** | 11 |
| A-602 급여명세서 발송 | 발송 API가 없다 | 8 |

### 새로 드릴 요청 — 서명 세 자리

신청서 · 연차사용계획서 · 단체연차에 **직원 서명 자리가 필요하다** (12번).
단체연차는 `apply`가 서버에서 신청서를 대신 만들어 **서명이 빠진다** — 종이로는 각자
도장을 찍는 자리다. 크기 상한(13번)과 배경(14번)도 8-31에 넘긴 실측값에 대한 답을 기다린다.

**관리팀 결재 화면에는 서명칸을 이미 만들어 뒀다** — 그리면 `IMAGE`, 비워두면 `CLICK`이다.

### 곁들여 해 둔 것

- API **12개 태그 61개 경로**를 전부 문서로 정리했다 (`API_*.md`)
- 목 데이터로 **열두 화면의 레이아웃·키보드 접근성**을 쟀다 — 1280px과 크롬 최소 글꼴
  20px에서 가로 스크롤·잘림 0, 표의 줄을 키보드로 열 수 있다
- 회사 서식(휴가신청서·촉구서·계획서·근태 자료)에서 **촉진 조건과 직군별 공제 규칙**을
  옮겨 적었다 (`API_연차.md` 10장, `API_근태.md` 8장)
- 모바일의 **시스템 글꼴 확대**를 쟀다 (2026-09-03) — `ListRow`에서 **급여 금액이 잘리는
  것**을 찾아 고쳤다. 3.12배까지 넘치는 줄이 0이 됐고 1.35배까지는 전과 같이 보인다

## 앱 개발을 막고 있는 것 (우선순위)

1. **인증 방식** — **거의 풀렸다** (2026-09-01 서버 답 「HRM 로그인 붙이기」).

   **방식이 우리가 생각한 것과 달랐다.** 프런트가 Keycloak과 직접 말하는 것이 아니라
   **서버가 로그인을 중계하고 프런트에는 토큰만 넘긴다.** public client도 PKCE도 OIDC
   라이브러리도 필요 없고, SSO 팀 terraform 작업도 필요 없다.

   **관리팀 콜백은 이미 등록돼 있다** — `/auth/callback`을 `localhost` 5173·3000과
   `127.0.0.1` 네 조합으로 열어 뒀다.

   **우리 코드는 거의 맞아 있었다.** fragment(`#token=`)로 받는 것, `sessionStorage`에
   두고 `localStorage`를 피하는 것, `Authorization: Bearer`, `/auth/me`로 권한을 받는 것,
   401 재이동을 한 번으로 막는 것까지 서버 안내와 같다. 고친 것은 둘이다 —
   로그인 입구를 `/auth/login`으로 바꾼 것과, **모바일이 `redirect`를 안 싣던 버그**다
   (`callbackUrl()`을 만들어 두고 `loginUrl()`에 붙이지 않아 토큰이 앱으로 올 수 없었다).

   **남은 것은 셋이고 둘은 우리 몫이다.**

   | 무엇 | 누가 |
   |---|---|
   | Keycloak 회원가입하고 아이디 알려주기 (`/hi-yo/auth/login`에서 Register, 영문 아이디) | **우리** |
   | SSO 팀에 `/engineering` 그룹 배정 요청 | **우리** |
   | `hr://auth/callback` 등록 | 서버 |

   셋 다 되어야 하고, 하나라도 빠지면 똑같이 `401`이다. 응답으로는 구분되지 않고
   이유는 서버 로그에만 남는다.

   **스텁 헤더 `X-Debug-Employee-No`는 9-01자로 서버가 지웠다.** 그 헤더 없이도 관리팀으로
   통과시키던 것이 우리가 보고한 「재직증명서 권한 구멍」의 정체였고 서버가 그렇게 확인해 줬다.

   붙일 때 지킬 것 둘 —
   - **`GET /auth/me`로 권한을 받는다.** `{ employeeId, employeeNo, name, role, admin }`
   - **토큰의 `resource_access`를 직접 읽지 않는다.** 병행 기간에는 앱 DB의 권한이 이겨서,
     토큰은 `user`인데 실제로는 관리팀인 사람이 있다 — 우리 네 계정이 정확히 그 경우다

### 목록 검색·필터는 서버가 통째로 주는 목록에만 붙인다 (2026-09-02)

관리팀 화면에 이름·부서로 찾는 칸이 없었다. 붙일 수 있는 곳과 없는 곳이 갈린다.

| 화면 | 목록이 오는 방식 | 붙였나 |
|---|---|---|
| 직원 (A-102) | 쪽으로 잘려 온다 | **서버 파라미터로 이미 있다** (`keyword`·`status`·`departmentId`) |
| 연차관리대장 (A-303) | 전 직원 배열 | **붙였다** — 이름·사번 검색, 부서 |

있는 사람은 없는 것처럼 보이고, 관리팀은 없는 줄 알고 넘어간다. `DESIGN_ADMIN.md` 8장이

**A-302는 서버에 찾는 파라미터가 없어서 못 붙였다** — 필요하면 서버에 요청할 일이다.

거르는 규칙은 `apps/admin/src/lib/listFilter.ts` 한 곳에 뒀다. 부서 목록은 **받은 줄에서**
만든다 — 마스터(`GET /departments`)를 따로 부르지 않는다. 표에 없는 부서를 골라 빈 표를
보게 할 이유가 없고, 마스터의 `id`와 줄의 부서 **이름**을 맞추는 문제도 생기지 않는다
(같은 문제로 A-102 수정 화면이 막혀 있다).

**요약 줄은 거른 결과를 따라가지 않는다.** `2026년 대장 46명`은 대장 전체를 말하는 값이고,

### S-503 교체 동의 화면을 만든다 (2026-08-28 확정)

명세서 흐름은 "교체 신청 → **상대방 동의** 대기(24시간) → 확정"이고, 알림 트리거표(6장)도
교체 요청을 **상대방에게 앱 푸시**로 보낸다고 적고 있다. 그런데 **동의를 누를 화면이
화면 인벤토리 25개 어디에도 없다.** 푸시를 받고 열 데가 없는 상태다.

**S-503 안에 "나에게 온 교체 요청" 영역을 만든다.** 별도 화면번호를 새로 파지 않는다 —
같은 명단·같은 스케줄을 보는 화면이고, 본인용 화면을 늘리면 하단 메뉴가 같이 늘어난다.

**API는 전부 있다 (2026-08-28 Swagger·실호출 확인).** 명세서보다 API가 더 자세하다.

| 경로 | 쓰는 곳 |
|---|---|
| `GET /duty/schedules/{employeeId}` | 내 당직 일정 (`from`·`to` 필수) |
| `GET /duty/swaps/inbox` | **나에게 온 교체 요청 — 마감 임박 순** |
| `POST /duty/swaps/{swapId}/decision` | 동의·거절 (`agreed` 필수, `comment` 선택) |
| `POST /duty/schedules/{scheduleId}/swaps` | 교체 신청 (`targetId` 필수, `reason` 선택) |
| `GET /duty/swaps/sent` | 내가 보낸 요청 |
| `DELETE /duty/swaps/{swapId}` | 신청 취소 |
| `GET /duty/rosters` | 명단·슬롯 정의 |

명세서에 없던 것이 API에서 풀렸다.

- **교체 상대방은 그 명단 안의 사람만 된다.** `POST /duty/schedules/{scheduleId}/swaps`가
  "본인 당직만, 명단 안의 사람에게만 보낼 수 있다"고 적고 있고 서버가 검증한다.
  후보 목록은 `GET /duty/rosters/{rosterId}/members`다. **앱에서 후보를 추려내지 않는다**
- **`EXPIRED`와 `REJECTED`를 구분해 보여줘야 한다.** `DutySwapResponse`가 명시적으로 요구한다 —
  "`EXPIRED`는 거절과 다르다. 상대방이 못 본 것이므로 다시 요청하거나 다른 사람에게 부탁할 수 있다"
- `DutyScheduleResponse.swapPending`으로 교체 요청이 걸린 배정을 표시할 수 있다
- 경비교대는 `useSlot: true`에 `slotCode`(`LUNCH` 11:30~12:00 / `DINNER` 16:30~17:00)로 온다.
  같은 날짜에 두 건이 오며 각각 별개 배정이다. 하루 단위 일괄 교체 버튼을 만들지 않는다

**만든 것은 확인과 응답까지다.** 부탁하는 쪽은 만들지 않았다 —
`targetId`를 고를 방법이 없다 (아래 「서버에 알려야 할 것」). 화면 이름이
"확인·교체 신청"이지만 지금 만들 수 있는 절반이 그렇다.

| 만든 것 | 안 만든 것 |
|---|---|
| 내 당직 달력·목록 | **교체 부탁하기 — 후보를 볼 수 없다. 이것 하나뿐이다** |
| 나에게 온 부탁 목록·동의·거절 | |
| 내가 부탁한 것의 상태 (`EXPIRED`·`REJECTED` 구분) | |
| 보낸 부탁 취소 (확인 시트) | |

### A-504 당직 명단·스케줄 관리 (2026-08-28 만듦)

명세서는 A-504를 화면 인벤토리에만 두고 상세 스펙을 주지 않는다. 데이터 모델(1.4)과 API가
확정돼 있어 명세서 3장의 "그 외 화면은 데이터 모델 및 화면 인벤토리를 기준으로 준용한다"를
따랐다. 보험 요율을 올린 것과 같은 기준이다.

명단은 **서버가 정의해 준다.** 만들거나 지우는 API가 없다 — 화면도 만들지 않는다.
개발 서버에 셋이 있고 명세서 S-503의 세 명단과 정확히 맞는다.

| 명단 | 순환 | 자동 편성 | 슬롯 |
|---|---|---|---|
| 당직(일직) `DAY_DUTY` | `BIWEEKLY` (14일마다) | 가능 | 없음. 08:00~17:00 |
| 평일연장 `WEEKDAY_OVERTIME` | `ON_DEMAND` (수시) | **불가** | 없음 |
| 경비교대 `GUARD_SHIFT` | `DAILY` (매일) | 가능 | **중식 11:30~12:00 · 석식 16:30~17:00** |

화면에서 정한 것.

- **순번을 화면에서 다시 매기지 않는다.** 서버가 준 순서가 곧 도는 순서다.
  가나다순 정렬이 아니고, 관리팀이 정한 값 그대로 자동 편성이 돈다
- **자동 편성에 확인 대화상자를 두지 않는다.** 이미 배정된 날짜를 건드리지 않아 몇 번을
  다시 돌려도 안전하다. 되돌릴 수 없는 동작이 아니다 (`DESIGN_ADMIN.md` 6장)
- **연차와 겹친 배정(`conflicts`)은 표 위에 건수와 명단으로 남긴다.** 서버가 겹친 건을
  건너뛰지 않고 그대로 배정한 뒤 알려준다. 다음 순번으로 넘길지 사람을 바꿀지가 확정되지
  않아(서버 스펙 `OPEN-QUESTIONS E-8`) 화면도 대신 고치지 않는다
- **`자동 편성하기`에 `disabled`를 썼다.** 명단이 `autoAssignable: false`거나 대상자가 0명이면
  누를 수 없고 이유를 버튼 옆에 적는다. 사용자가 이 화면에서 고칠 수 없거나 고칠 곳이 따로
  있는 상태이며 서버도 같은 검증을 한다 — `DESIGN_ADMIN.md` 1장의 두 조건을 지켰다
- **배정 상태 문구는 API를 따랐다.** 명세서 1.4는 `예정/확정/완료`인데 API는
  `PLANNED/DONE/SWAPPED`를 준다. `확정`에 해당하는 값이 없고 `교체됨`이 명세서에 없다
- 상태를 그린으로 칠하지 않았다. 셋 중 어느 것도 A-601의 `확정`처럼 되돌릴 수 없는
  이정표가 아니라 그냥 시점이다. 이 화면의 그린은 `자동 편성하기` 하나다

**대상자를 아직 넣지 않았다.** 직원 103명이 실제 명단으로 보여 임의로 넣지 않았다.
명단 셋 다 `memberCount`가 `0`이고, 그래서 S-503도 열면 빈 상태만 보인다.

### A-503 52시간 근접 알림 현황 (2026-08-28 만듦)

서버가 `GET /attendance/weekly`를 **"52시간 근접 현황 — 관리팀 화면"**이라고 적어 두었다.
화면을 상정하고 만든 엔드포인트라 A-504와 같은 기준(명세서 3장 준용)으로 붙였다.

**단계는 서버가 정한다.** `WeeklyWorkSummaryResponse` 스키마가 직접 그렇게 적고 있다 —
"프런트가 분 단위로 다시 판단하면 서버와 기준이 어긋나므로 단계를 서버가 정합니다."

| `alertLevel` | 화면 문구 | tone |
|---|---|---|
| 0 | `여유 있어요` | neutral |
| 1 (48h) | `48시간을 넘겼어요` | neutral |
| 2 (52h 임박) | `52시간이 코앞이에요` | **error** |
| 3 (초과) | `52시간을 넘겼어요` | **error** |

**서버 설명은 이 단계를 "화면에서 색을 고르는 기준"이라고 하지만 색은 셋뿐이다.**
`DESIGN_ADMIN.md` 7장이 `done`·`error`·`neutral` 말고 새 tone을 만들지 못하게 하고 뱃지도 금지한다.
그래서 **경고(2)와 초과(3)를 같은 빨강**으로 두고 구분은 문구가 한다 — 넘긴 것과 넘길 것 둘 다
관리팀이 지금 손대야 하는 줄이라 같은 무게로 봤다.

그 밖에 정한 것.

- **거르는 것도 서버가 한다.** `onlyAlerted`를 서버에 넘긴다. 앱에서 `alertLevel`로 거르면
  기준이 어긋났을 때 관리팀이 놓치는 사람이 생긴다
- **기본값을 `알림 대상만`으로 둔다.** 주 52시간은 넘기면 회사가 처벌받는다.
  전 직원 표가 아니라 손댈 사람 명단으로 읽혀야 한다
- `remainingMinutes`는 넘겼으면 음수로 온다. `formatMinutes`가 부호를 붙이고,
  음수인 칸만 `danger` 글자로 둔다. **여기서 다시 계산하지 않는다**
- 조회만 하는 화면이라 primary 버튼이 없다. 그린도 없다 (`DESIGN_ADMIN.md` 7장 —
  조회가 목적인 화면은 1곳 이하가 정상이다)

**근태 기록이 서버에 하나도 없다.** `GET /attendance/weekly`도 `GET /attendance/daily`도
어느 주를 봐도 빈 배열이다 (2026-08-28 실호출). 세콤 수집(`POST /attendance/collect`)이
아직 안 돌았거나 원본이 없는 것으로 보인다. **그래서 값이 찬 표는 아직 못 봤다.**

날짜 표기는 `apps/admin/src/lib/datetime.ts`에 모았다. 관리팀 화면에는 날짜 라이브러리가 없고
이것 때문에 더하지 않았다 — `Intl`과 `Date.UTC`로 되는 범위다. A-504가 각자 갖고 있던
`todayInKst`·`weekdayText`도 같이 옮겼다.

### 공휴일 관리 (2026-08-31 만듦)

`apps/admin` `/holidays`. 화면번호가 없다 — 명세서 화면 인벤토리 25개에 없는 화면이다.
데이터 모델과 API가 확정돼 있어 명세서 3장의 준용 규칙을 따랐다 (A-504·A-503과 같은 기준).
메뉴는 **연차** 모듈에 넣었다. 연차 차감일이 이 목록을 보기 때문이다.

**이 화면이 급한 이유.** 서버가 아는 공휴일이 양력 고정일 9개뿐이라 지금 상태로 설 연휴에
연차를 신청하면 **연휴가 연차에서 깎인다**. 다른 화면을 만드는 것보다 이 입력이 먼저다.

화면에서 정한 것.

- **빠진 날을 화면이 찾아주지 않는다.** 설날·추석이 없다고 알리려면 음력을 계산해야 하고
  그건 문서에 없는 규칙이다 (`CLAUDE.md` 3장). 등록된 것을 연도별로 보여주는 데까지가 화면의
  일이고, 무엇이 빠졌는지는 사람이 달력을 보고 판단한다. 대신 **건수를 표 위에 적었다** —

- **요일 열을 넣었다.** 등록 대화상자도 고른 날짜의 요일을 아래에 보여준다. 토·일에 넣고 있으면
  손이 미끄러진 것이거나 대체공휴일을 같이 넣어야 하는 날이다
- **고를 수 있는 연도는 올해와 내년뿐이다.** 등록된 연도를 서버에서 알아낼 방법이 없다 —
  `/years` 경로가 없고 `year`를 비우면 전체가 오지 않는다 (`API_연차.md` 9장).
  지난 해는 계산이 이미 끝났고 지워도 되돌아가지 않아 목록에 두지 않았다
- **삭제에 `danger` 버튼과 확인 대화상자를 썼다.** 지우면 이후 계산에서 그날이 근무일이 되고,
  이미 그 날짜로 계산된 연차는 되돌아가지 않는다 (`DESIGN_ADMIN.md` 5·6장)
- 수정 API가 없다. 고치는 화면을 만들지 않았다 — 지우고 다시 넣는다

**`holidayType`이 풀렸다.** `PUBLIC`·`COMPANY` 두 값이다 (`API_연차.md` 9장).
다만 **구분에 따라 연차 차감이 달라지는지는 모른다** — 회사 지정 휴무일을 넣기 전에 확인한다.

**103명 전원이 `insufficient`로 나올 것으로 보인다.**

### A-303 연차관리대장 (2026-09-01 만듦)

`apps/admin` `/leave-ledger`. `GET /leave/ledger?year=` 하나만 부르는 조회 화면이다.

**이 화면의 목적은 잔여 확인이 아니라 누락 찾기다.** 서버가 연차를 자동으로 부여하지 않고
관리팀이 산정한 값을 입력받는 구조라(2026-08-31 서버 답변), 안 넣으면 그 사람은 한 해를
0일로 보낸다. 서버가 발생 0인 직원까지 대장에 넣어 주는 이유가 그것이다.

화면에서 정한 것.

- **`noGrant`를 `0일`로 그리지 않는다.** 발생 칸에 `아직 안 넣었어요`를 `danger` 글자로
  적었다. 둘을 다 `0일`로 그리면 이 화면이 할 일이 없어진다. 행 배경은 칠하지 않았다
  (`DESIGN_ADMIN.md` 3장 「경고 행」)

  `onlyAlerted`를 주고 단계도 서버가 매기니 화면이 다시 거르면 기준이 어긋난다.
  대장은 서버에 거르는 파라미터가 없고 `noGrant`가 서버가 준 참·거짓 그대로라
  다시 판정하는 것이 아니다
- **연도 목록을 올해와 지난 두 해로 뒀다.** 서버가 연도 목록을 주지 않는다. 공휴일과 같은
  사정인데 범위가 반대다 — 대장은 지나간 해를 들춰보는 장부라 내년이 아니라 지난 해가
  필요하다. 더 옛 해가 필요해지면 화면에서 넓히지 않고 서버에 목록을 요청한다
- **잔여는 `remaining`이다.** 결재 대기까지 뺀 값으로 확정돼 있다 (`API_연차.md`
  「잔여는 어느 값인가」). 화면에서 `granted - used - pending`을 하지 않는다
- 조회만 하는 화면이라 primary 버튼이 없고 그린도 없다 (`DESIGN_ADMIN.md` 7장)

**A-306 신입휴가 수동 입력(발생 등록)은 만들지 않았다.** `POST/PUT/DELETE /leave/grants`가
열려 있으나 두 가지가 비어 있다 — 관리팀이 **무엇을 몇 일 넣어야 하는지**(연차 발생 규칙,
명세서 8장 2번)와 **`grantType` 다섯 개(`MONTHLY`·`REGULAR`·`SENIORITY`·`NEW_HIRE`·
`CARRY_DEDUCT`)가 각각 무슨 뜻인지**다. 종류를 잘못 고르면 발생 일수가 틀리게 쌓이고
그것이 전 직원의 잔여가 된다. `CLAUDE.md` 3장의 추측 금지 항목이라 멈췄다.

**`expiresOn`은 풀렸다** (2026-09-01 스웨거 재확인). 비우면 **그해 12월 31일**이 되고,
근거는 **이월이 없다**는 것이다. 스키마 설명에 적혀 있다 — `API_연차.md` 7장 3번을 닫았다.

**빈 화면만 확인했다.** 발생이 0건이라 대장은 전원 `noGrant`로 오고, 지금은 그마저도
서버가 `401`이라(아래 「앱 개발을 막고 있는 것」 1번) 실제 줄을 그려 본 적이 없다.

### A-501 전 직원 근태 현황 (2026-09-01 만듦)

`apps/admin` `/attendance`. `GET /attendance/daily?date=` 하나만 부르는 조회 화면이다.
스펙이 이 경로를 직접 "관리팀 화면"이라고 적고 있다.

**이 화면의 목적은 근무시간 확인이 아니라 덜 끝난 날 찾기다.** 판정이 확정되지 않은
날이 남아 있으면 **그 사람은 급여 계산에서 통째로 빠진다** (`skipped`, `API_급여.md`).
월말에 발견하면 이미 늦다.

화면에서 정한 것.

- **분 필드 열둘 중 일곱만 뒀다.** 출근·퇴근·급여기준·연장·야간·당직·지각·조퇴를 두고
  기본·법정·휴일·휴일연장·주휴는 뺐다. 그것들은 한 달치를 항목별로 쌓아 보는
  급여대장(A-601)이 읽는 값이다. 명세서의 필드를 순서대로 늘어놓지 않는다
  (`CLAUDE.md` 8장). **빠진 다섯이 하루 단위로도 필요하면 다시 넣는다**
- **자정을 넘긴 퇴근에 `+1`을 붙인다.** 야간근무는 `checkOutAt`의 **날짜**가 하루 뒤로
  온다. 시각만 떼어 `01:30`으로 적으면 새벽에 출근한 것으로 읽힌다.
  `lib/datetime.ts`의 `formatKstClock`이 근무일과 비교해 붙인다
- **퇴근 기록 없음을 출근이 찍힌 날에만 빨강으로 적는다.** 둘 다 없으면 안 나온 날이라
  누락이 아니다. 두 값을 읽은 것이지 근태를 판정한 것이 아니다
- **`판정 완료`를 그린으로 두지 않았다.** `DESIGN_ADMIN.md` 7장의 `done`이 확정에 쓰는
  색이고 판정 확정도 거기 들지만, 정상인 줄이 대부분이라 초록이 깔리면 손대야 할 줄이
  묻힌다. A-503에서 `여유 있어요`를 무채색으로 둔 것과 같은 판단이다.
  `판정 전`은 빨강이다 — 7장이 `error`의 예로 **근태 누락**을 직접 들고 있다
- 조회만 하는 화면이라 primary 버튼이 없고 그린도 없다

**보정 · 판정 재실행 · 세콤 수집은 넣지 않았다.** API 셋 다 열려 있는데 화면 인벤토리에
자리가 없다 — 근태 화면 셋(A-501·A-502·A-503)의 유형이 전부 조회 아니면 승인이다.
인벤토리가 A-501을 조회로 못박고 있고, 판정 재실행은 그 날 전 직원의 연장·야간·지각을
다시 매기는 동작이라 조회 화면에 곁들일 무게가 아니다. **기획에 물어야 한다**
(`API_근태.md` 7장 5번).

**빈 화면만 확인했다.** 서버가 수집기 버그 셋을 고쳤다고 했으나(2026-08-31) 인증이
막혀 있어 값이 찬 화면을 아직 보지 못했다. 로그인이 뚫리면 A-503·S-501과 같이 본다.

### A-502 신청형 근태 승인 — 나눌 수 없다 (2026-09-01 확인)

만들려다 멈췄다. **서버가 A-302와 A-502를 나눌 재료를 주지 않는다.**

- `GET /requests/pending`의 파라미터는 `pageable` 하나뿐이다. 종류로 거르는 값이 없다
- `RequestTypeResponse`에 모듈 구분이 없다. `deductLeave`·`deductPay`·`needTime`·
  `halfDay` 네 개는 **폼의 모양**을 정하는 값이지 "이건 연차, 이건 근태"가 아니다
- 11개 종류를 앱이 두 무리로 갈라야 하는데 그 기준이 문서 어디에도 없다.
  외출·조퇴는 근태처럼 보이지만 특별(경조사)·교육·유급휴가는 어느 쪽인지 알 수 없다

**기능이 빠진 것이 아니다.** 지금 A-302 화면(`/approvals`)이 대기 목록 전부를 보여주고
종류 칸에 서버가 준 `typeName`이 그대로 나온다 — 외출·조퇴·교육도 거기서 결재된다.

나누려면 서버가 둘 중 하나를 줘야 한다 — **`pending`에 종류 필터**, 또는
**`RequestTypeResponse`에 모듈 구분.** 둘 다 없으면 나누지 않는다. 앱이 11개를 임의로
가르면 어느 쪽에도 안 나오는 종류가 생기고, 그 신청은 아무도 결재하지 않은 채 남는다.

### A-301 전 직원 연차 현황 (달력) (2026-09-01 만듦)

`apps/admin` `/leave-calendar`. `GET /leave/calendar/all?from=&to=` + `GET /holidays?year=`.

**대장(A-303)이 한 사람의 한 해를 세로로 본다면 이쪽은 하루를 가로로 본다.** 관리팀이
이 화면을 여는 이유는 잔여를 확인하려는 것이 아니라 **자리가 비는 날을 미리 보려는 것**이다.

**관리팀 화면에 달력 컴포넌트를 새로 만들었다** (`src/components/Calendar.tsx`).
`DESIGN_RULES.md` 1장 3번에 따라 만들기 전에 물었고 승인받았다 (2026-09-01).
모바일 `Calendar`를 나눠 쓸 수 없다 — React Native이기도 하고, 하는 일이 다르다.
그쪽은 본인 하루에 점 하나를 찍고 **날짜를 고르는 입력칸**이고, 이쪽은 여러 사람의
이름을 칸에 늘어놓는 **읽는 격자**다.

화면에서 정한 것.

- **칸에 건수가 아니라 이름을 적는다.** 셋이 쉬는 날에 `3건`이라고만 적으면 그 셋이
  같은 팀인지 알 수 없다 — 자리가 비는지 보려는 화면인데 그걸 알 수 없으면 소용이 없다.
  종류는 서버가 준 `typeName`을 그대로 옆에 둔다
- **`from`·`to`에 격자의 처음과 끝을 넘긴다.** 그 달의 1일~말일이 아니다. 격자가 앞뒤 달
  날짜까지 덮으므로 1일~말일만 부르면 첫 줄과 마지막 줄에 걸친 날이 비어 보인다
- **공휴일을 같이 깐다.** 아무도 안 쉬는 날이 공휴일이라서인지 그냥 빈 날인지 구분이
  안 되면 달력을 잘못 읽는다. 이미 있는 `useHolidays`를 그대로 부른다 — 새 API가 아니다
- **칸에 세로선을 그었다.** 표에서 세로선을 긋지 않는 규칙(`DESIGN_ADMIN.md` 3장)은 열이
  스무 개까지 늘어나는 표 이야기다. 달력은 일곱 칸이 고정이고, 세로선이 없으면 이름들이
  어느 날 것인지 흐려진다
- **사람이 몰린 날은 칸이 늘어난다.** 넘치는 인원을 `+3명`으로 접지 않았다 — 몰린 것이
  이 화면이 보여줘야 하는 바로 그 신호인데 접으면 그게 사라진다
- **로딩·오류에도 격자를 지우지 않는다.** 달력은 서버 응답이 없어도 그 달의 모양 자체가
  정보다. 빈 상태는 두지 않았다 — 아무도 안 쉬는 달은 정상이고, 빈 격자가 이미 답이다
- 조회만 하는 화면이라 primary 버튼이 없고 그린도 없다

**격자·여백·공휴일 표시를 실제로 그려서 확인했다** (2026-09-01). 서버가 `401`이라 앱을
띄울 수 없어, 빌드된 CSS에 토큰을 심고 컴포넌트가 내는 것과 같은 마크업으로 렌더해 봤다.
1266px에서 칸 하나가 169px이고 이름+종류가 들어간다. 그 과정에서 둘을 고쳤다 —
달 이름이 한쪽으로 쏠려 있던 것과, 마지막 줄 밑줄이 상자 테두리와 겹쳐 2px로 보이던 것.
**값이 찬 진짜 화면은 아직 못 봤다** — 연차 신청이 0건이다.

### S-301 신청 종류를 고를 수 있게 했다 (2026-09-01)

그전에는 `typeCode: 'ANNUAL'`이 화면에 박혀 있어 **연차만 낼 수 있었다.** 반차를 못 낸
이유는 코드가 아니라 시각이었다 — API가 `startTime`·`endTime`을 요구하는데 오전·오후가
몇 시부터인지가 정해져 있지 않았다. 인사팀이 확정해 줘서 풀렸다.

| 반차 | 시각 |
|---|---|
| 오전 | `09:00` ~ `13:00` |
| 오후 | `13:00` ~ `18:00` |

**점심시간이 반차 시간에 포함된다.** 그래서 오전과 오후의 길이가 다르다 — 앱이 고칠 일이
아니고, 몇 일이 깎이는지는 서버가 정한다.

화면에서 정한 것.

- **어떤 칸이 필요한지를 서버가 정한다.** `GET /requests/types`의 `halfDay`면 오전·오후를
  고르고, 그 밖의 `needTime`이면 시각을 직접 받아야 한다. 코드로 분기하지 않는다
- **종류 이름은 서버가 준 `name`을 그대로 쓴다.** 새 종류가 늘어도 화면을 안 고친다
- **연차휴가로 시작한다.** 이 화면이 연차 화면이라 그렇게 뒀다 — 규칙이 아니라 기본값이다.
  서버 목록에 `ANNUAL`이 없으면 아무것도 안 고른 채로 두고 사용자가 고른다
- **반차 시각을 앱이 갖고 있다.** `RequestTypeResponse`에 시각 필드가 없어서다.
  회사가 시각을 바꾸면 앱을 다시 배포해야 한다 — **종류 응답에 실어달라고 요청했다**
- 사유 입력이 200자에서 잘리고 있었다. 서버 한계인 **255**로 고쳤다

**외출·조퇴도 낼 수 있다 — `TimeField`를 만들었다** (2026-09-01 승인).
`src/components/TimeField.tsx`. 이제 종류를 하나도 빼지 않는다.

- **네이티브 시간 피커를 쓰지 않는다.** `SelectSheet`가 목록 시트를 쓰는 이유와 같다 —
  iOS 휠과 안드로이드 시계는 모양이 서로 다르고 디자인 시스템이 닿지 않는다.
  라이브러리도 더하지 않았다
- **목록에서 고르게 하지 않았다.** 30분·10분 단위 목록을 주면 `14:20`에 나간 사람이
  자기 시각을 적을 수 없다. 몇 분 단위로 끊는지는 문서에 없는 규칙이라 화면이 정하지
  않는다 (`CLAUDE.md` 3장). 종이 신청서도 시각 칸이 빈칸이다
- **`TextField` 위에 얹었다.** 테두리·글꼴·오류 표기가 다른 입력칸과 같아야 하고,
  시스템 글꼴을 키우면 같이 늘어나야 한다. `TextField`에는 `keyboardType` 하나만 더했다
- **다 적기 전에는 나무라지 않는다.** 네 자리를 다 적었는데 시각이 아닐 때만 알린다
- **시작이 끝보다 늦은지는 보지 않는다.** 서버가 판정할 일이다

**시각이 덜 채워진 채로는 보내지 않는다.** 반쪽짜리로 보내면 서버가 400을 돌려주는데,
그건 화면이 이미 아는 것이라 물어볼 일이 아니다. 왜 안 나가는지는 버튼 위에 적는다 —
잔여 초과처럼 **서버가 판단하는 것은 여전히 막지 않는다** (S-301 확정 결정).

**비상연락처는 넣지 않았다.** 종이 양식에 있고 API도 받지만(`emergencyContact`, 50자)
이번에 막혀 있던 것이 아니라 손대지 않았다.

**실기기로 확인하지 못했다.** Expo Go로는 이 프로젝트가 안 뜨고 EAS 개발 빌드가 필요한데,
서버가 `401`이라 종류 목록부터 못 받는다.

### 근태 정리 (2026-09-01 만듦)

`apps/admin` `/attendance/operations`. 좌측 메뉴 `근태 > 근태 정리`.
**화면번호가 없다** — 인벤토리 25개에 없고, 기획이 새 화면으로 만들라고 정했다 (2026-09-01).
명세서 3장의 준용 규칙을 따랐다 (A-504·A-503·공휴일과 같은 기준).

세콤 태그가 근태가 되기까지 두 단계를 거친다.

```
수신 버퍼 ──(수집)──> 근태 기록 ──(판정)──> 판정 완료 ──> 주간 집계
```

정기 배치가 따로 돌지만 관리팀이 "지금 반영"을 눌러야 하는 경우가 있어 서버가 두 경로를
열어 뒀다. **그 자리가 이 화면이다.**

화면에서 정한 것.

- **기준일 하나가 화면 전체를 몬다.** 그 날 근태 목록에서 고칠 사람을 고른다 — 직원을 따로
  찾는 칸을 두지 않았다
- **동작을 상자 안에 뒀다.** 제목 줄 오른쪽에 주 동작을 두는 규칙(`DESIGN_ADMIN.md` 11장)은
  주 동작이 하나일 때 이야기다. 여기는 셋이고 각각 다른 상자에 속해서, 같은 상자의 실행
  줄에 두는 쪽이 무엇을 누르는 것인지 읽힌다
- **수집은 날짜를 안 받는다.** 파라미터가 없어 버퍼를 통째로 옮긴다 — 기준일과 무관하다는
  것을 화면에도 적었다
- **`changed`를 그냥 넘기지 않는다.** "그만큼 재판정이 필요하다"가 스키마 설명이라, 0보다
  크면 다시 판정하라고 적는다. `skipped`는 빨강이다 — 사람이 봐야 하는 건이다
- **판정 재실행에 확인 대화상자를 두지 않았다.** 여러 번 돌려도 같은 결과라 되돌릴 것이
  없다 (`DESIGN_ADMIN.md` 6장). **확정에는 뒀다** — 급여로 넘어가는 이정표다
- **보정에 `danger`를 쓰지 않았다.** 원본을 고치지 않고 보정만 쌓아서 되돌릴 수 없는 동작이
  아니다. 잘못 넣었으면 다시 보정한다
- **보정은 날짜와 시각을 따로 받는다.** 야간근무는 퇴근이 다음 날이라 시각만 받으면 새벽
  퇴근을 적을 방법이 없다. 관리팀 `Field`에 `time`을 더했다 — 브라우저에 시각 입력이 있어서
  모바일과 달리 새로 만들 이유가 없었다
- **고칠 쪽만 보낸다.** 비워 둔 쪽은 원본이 그대로 남는다고 스펙이 적고 있다. 한쪽이라도
  덜 채워졌으면 보내지 않는다 — 반쪽짜리를 보내면 원본이 엉뚱한 값으로 덮인다

**확정을 되돌리는 경로가 없다** (`API_근태.md` 7장 6번). 화면이 대신 정하지 않고 확인
대화상자에 "되돌리는 경로가 스펙에 없어요"를 그대로 적었다.

**빈 화면만 확인했다** — 서버가 `401`이다. 상자·표 배치는 빌드된 CSS로 렌더해 눈으로 봤다.

### ~~재직증명서 단건·PDF에 권한 검증이 없다~~ — 구멍이 아니었다 (2026-08-31 해소)

**2026-08-26에 아래 결과를 보고 권한 검증이 없다고 적었다. 틀린 진단이었다.**

원인은 스텁 인증이다 — `STUB_USER=employee:1`이 `ADMIN`이라, 헤더 없이 부르면 관리팀으로
로그인된 상태가 된다. `canAccess()`가 `isAdmin() || 본인`이라 전부 통과한다.
**"인증 헤더 없음 → 200"이 오히려 그 증거다** — 진짜로 인증이 없었다면 401이 났어야 한다.
oauth 모드에서는 재현되지 않는다 (서버가 같은 날 실호출로 확인).

자세한 것은 `API_재직증명서.md` 5장 1번에 있다. 아래는 당시 관측이다.

| 요청 | 결과 |
|---|---|
| `GET /certificates/1` — 발급자 본인 (`employee:2`) | `200` |
| `GET /certificates/1` — **다른 직원** (`employee:3`) | `200` — 남의 증명서가 그대로 나온다 |
| `GET /certificates/1/pdf` — **다른 직원** (`employee:3`) | `200` — PDF까지 받아진다 |
| `GET /certificates/1/pdf` — **인증 헤더 없음** | `200` — 그대로 받아진다 |
| `GET /certificates` (목록) — 다른 직원 | `200`, `totalElements=0` — 목록은 격리돼 있다 |

증명서에는 성명·부서·재직기간이 들어가고, 주민등록번호와 현주소도 등록되면 들어간다.
id가 `1`부터 순번이라 훑기도 쉽다. **목록만 막고 단건·PDF가 열려 있다.**

앱은 본인 id로만 호출하므로 이 구멍을 쓰지 않는다. 그러나 클라이언트가 막을 수 있는 문제가 아니다.
서버에서 요청자와 증명서 소유자를 대조해야 한다.

**위 표의 증명서 `id=1`은 지금 없다** — 시드가 다시 심어졌다 (2026-08-28). 고쳐졌는지는 확인하지
못했다. 구멍이 남아 있는지 다시 보려면 증명서를 새로 발급하고 다른 직원 id로 불러봐야 한다.

### 교체 상대 후보를 본인이 볼 수 없다 (2026-08-28 확인)

**S-503의 교체 신청 절반을 막고 있다.**

`POST /duty/schedules/{scheduleId}/swaps`는 `targetId`가 필수다. 그런데 **일반 직원은
누구에게 부탁할 수 있는지 알아낼 방법이 없다.** 후보를 담은 두 경로가 모두 막혀 있다.

| 요청 | `employee:1` (관리팀) | `employee:2` · `employee:3` |
|---|---|---|
| `GET /duty/rosters/{id}/members` — 명단 대상자 | `200` | **`403`** |
| `GET /duty/schedules` — 당직표 전체 | `200` | **`403`** |
| `GET /duty/rosters` — 명단 정의 | `200` | `200` |
| `GET /duty/swaps/inbox` · `/sent` | `200` | `200` |
| `GET /duty/schedules/{내 id}` | `200` | `200` |

Swagger에는 `GET /duty/rosters/{id}/members`에 **`관리팀만` 표시가 없다.** 같은 태그의
`POST`·`DELETE`·`PATCH`에는 붙어 있어서 조회는 열려 있는 것으로 읽힌다. 실제로는 막혀 있다.
스펙과 동작 중 어느 쪽이 의도인지 정해야 한다.

- 의도가 "본인도 명단을 본다"면 → `GET /duty/rosters/{id}/members`를 본인에게 열어준다
- 의도가 "명단은 관리팀만 본다"면 → **부탁할 상대를 고를 다른 방법이 필요하다.**
  같은 명단에 속한 사람만 담은 조회를 따로 열거나, `targetId` 없이 명단 전체에 부탁을
  거는 방식이 있어야 한다

그때까지 S-503은 확인과 응답까지만 만들었다. 부탁하는 화면은 만들지 않았다.

**권한이 제대로 걸려 있는 것도 확인했다.** `GET /duty/schedules/{employeeId}`에 다른
직원의 id를 넣으면 `403`이다. 재직증명서 단건·PDF가 열려 있는 것(위)과 대조된다 —
당직 쪽은 요청자와 대상자를 대조하고 있다.

### `PUT /employees/{id}`가 전체 교체라 주민등록번호가 지워진다 (2026-08-26 확인)

**A-102 수정 화면을 만들 수 없는 이유다.**

`PUT /employees/{id}`는 보내지 않은 필드를 지운다. 개발 서버에 실호출해 확인했다.

```
사원001 원본        부서=임원, 직무=사무직
PUT (필수 3개만)    부서=null, 직무=null      ← 생략한 필드가 지워졌다
```

(확인 후 원래 값으로 되돌려 두었다.)

`EmployeeUpdateRequest`에는 `residentNo`가 들어 있다. 그런데 **주민등록번호는 어떤 조회
응답에도 담기지 않는다** — `EmployeeResponse`는 "어떤 경우에도 담지 않는다", `EmployeeDetailResponse`는
"재직증명서 출력 경로에서만 쓰이므로 여기에 담지 않는다"고 스펙에 적혀 있다.
화면이 받을 수 있는 것은 `residentNoRegistered` 불리언뿐이다.

**읽을 수 없는 값을 다시 보낼 방법이 없다.** 그래서 직원 정보를 한 번 수정할 때마다
주민등록번호가 지워진다. 그러면 그 직원은 재직증명서를 발급받지 못한다.

클라이언트가 막을 수 있는 문제가 아니다.

#### 요청 — `PATCH /employees/{id}/resident-no` 를 열어달라 (2026-08-28)

이 리포지토리는 **같은 이유로 PUT에서 빠져나온 엔드포인트를 이미 둘 쓰고 있다.**

| 엔드포인트 | 하는 일 |
|---|---|
| `PATCH /employees/{id}/employee-no` | 사번 부여 |
| `PATCH /employees/{id}/status` | 휴직·복직·퇴사 |

주민등록번호도 같은 모양으로 분리하면 된다. `PUT`을 부분 수정으로 바꾸는 것보다 범위가 좁고,
이미 있는 패턴이라 클라이언트 쪽 변경도 `useAssignEmployeeNo`와 같은 형태 하나 늘리는 것으로 끝난다.

**우회(PUT에 읽은 값을 전부 다시 실어 보내기)가 위태로운 이유.**

계좌정보는 걱정하지 않아도 된다 — `EmployeeUpdateRequest`에 **계좌 필드가 없다.**
`PUT /employees/{id}/bank-account`로 이미 분리돼 있고 스키마 설명도 그렇게 적고 있다
(2026-08-28 Swagger 확인. 2026-08-26자 초안에 "계좌번호가 마스킹 값으로 덮어써진다"고 적었던 것은
틀렸다). 계좌는 이 문제의 사례가 아니라 **이미 올바르게 분리된 선례**다.

남는 문제는 둘이다.

- **`departmentId`·`jobId`를 되돌려 보낼 수 없다.** `EmployeeUpdateRequest`는 id를 받는데
  조회 응답은 `departmentName`·`jobName`만 준다. 이름으로 id를 역매핑해야 하고,
  이름이 겹치거나 부서명이 바뀌면 엉뚱한 부서로 옮겨진다
- **주민번호 하나 넣자고 인적사항 16개 필드를 전부 다시 쓰는 요청을 보내게 된다.**
  그 사이 다른 사람이 수정한 값을 덮어쓴다

`phone`·`email`·`address`가 마스킹돼 오는지는 **확인하지 못했다.** 개발 서버 직원 103명 전원이
이 값들이 `null`이다. 마스킹돼 온다면 위 우회는 연락처까지 망가뜨린다.

그때까지 A-102는 등록·재직상태 변경·사번 부여만 만들었다. 인적사항 수정은 만들지 않았다.
주민등록번호 등록 화면도 이 엔드포인트가 열리기 전까지 만들지 않는다.

**세콤 인사정보 102명 + 관리팀 자료**(연차관리대장·월간근태현황·급여대장)로 다시 만들었다.

앞으로 데이터를 건드릴 일이 있으면 먼저 알려주기로 했다.

### 주민등록번호 입력 경로가 화면 스펙에 없다 (2026-08-26, 2026-08-28 갱신)

명세서 A-102의 필드 목록에 주민등록번호가 없다. 그런데 재직증명서에는 들어가야 한다.

**어느 화면에서 입력할지는 정했다** — 관리팀 전용 등록 화면을 신설한다

**누가 입력하는가도 정해졌다 (2026-09-01 인사팀). 관리팀 전원이다.**

요청할 필요가 없다. 남은 것은 `PATCH /employees/{id}/resident-no` 하나뿐이다.

### 그 밖에 확인된 차이

- `POST /certificates`는 **201**을 준다. Swagger에는 200으로 선언돼 있다.
  **201이 맞고 스펙이 틀렸다** — 서버가 문서를 고치기로 했다 (2026-08-31).
- 값 검증 실패는 **400** `"요청 값이 올바르지 않습니다."`다. 업무 규칙 위반(422)과 다른 코드다 —
  앱의 오류 분기(`lib/apiError.ts`)는 이 구분을 그대로 따른다.

**눈으로 보면 겹치지 않는다** — 전부 한 줄짜리 요소여서 줄끼리 부딪히지 않는다.

### 하나 걸렸고 고쳤다 — 연차 달력의 이름 말줄임

최소 글꼴을 켜면 달력 칸의 이름이 말줄임으로 잘린다. **기본 글꼴에서는 한 건도 안 잘린다.**

| | 이름이 잘린 건수 |
|---|---|
| 기본 (1280·1600) | 0 / 56 |
| 최소 16px (1280) | 5 / 56 — 여섯 글자 이름만 |
| 최소 20px (1280) | **30 / 56 — 세 글자 이름도 `김…`이 된다** |
| 최소 20px (1600) | 5 / 56 |

달력은 **누가 쉬는지**를 보는 화면인데 이름이 한 글자만 남으면 목적을 잃는다.
`title`이 붙어 있어 마우스를 올리면 전체가 보이지만, 하루 네 명이면 네 번 올려야 한다.

**이름을 지키기로 했다 (2026-09-02).** `.calendar-entry`에 `flex-wrap: wrap`을 줘서
칸보다 길면 **종류가 다음 줄로 내려가고 이름은 온전히 남는다.** 세로 간격은 0이다 —
사람 사이가 2px인데 한 사람의 두 줄이 그보다 벌어지면 누구의 종류인지 읽히지 않는다.

**기본 글꼴에서는 아무것도 달라지지 않는다.** 같은 화면에서 규칙만 되돌려 재보니
격자 719px · 칸 최대 137px · 잘림 0으로 전후가 같다. 최소 20px에서는 잘림이 0/56이 되고
격자가 971px로 늘어난다 — 세로로 늘어날 뿐 가로 스크롤은 생기지 않는다.

1024px·최소 20px에서는 15/56이 남는다. 이름 하나가 칸보다 길어서인데 최소 지원 폭(1280)
밖이라 그대로 뒀다.

## 모바일 큰 글꼴 점검 (2026-09-03)

관리팀 웹은 9-02에 쟀는데 **모바일은 한 번도 재지 않았다.** `CLAUDE.md` 6장이 요구하는
쪽을 이번에 쟀다.

### 어떻게 쟀나 — 실기기가 아니다

**EAS 개발 빌드가 없어서 화면을 띄우지 못했다.** 대신 스크래치패드(리포 밖)에
`apps/mobile`의 스타일 값을 그대로 옮긴 페이지를 만들고, **리포에 있는 Pretendard
`.otf` 두 벌을 실제로 실어** 브라우저에서 요소 단위로 쟀다. 목 데이터는 리포에 안 들어간다.

React Native 의 기본값을 CSS 로 옮겼다 — `flexDirection: column`, `flexShrink: 0`,
`minWidth: 0`. 글꼴 배율은 `fontSize`에만 곱하고 `maxFontSizeMultiplier`가 있는 곳은
거기서 멈췄다 (RN 이 그렇게 동작한다. `lineHeight`에는 그 상한이 안 걸린다).

| 잰 것 | 값 |
|---|---|
| 화면 폭 | 375 (iPhone SE, 명세 기준) · 360 (안드로이드) · 320 (지원 폭 밖) |
| 글꼴 배율 | 1 · 1.15 · 1.3 · **1.35**(iOS 기본 최대) · 1.64 · 1.95 · **2**(안드로이드 최대) · 2.35 · 2.95 · **3.12**(iOS 접근성 최대) |

**브라우저 플렉스박스는 Yoga 가 아니다.** 넘칠 때의 셈이 완전히 같지는 않으므로 아래
숫자는 방향을 가리키는 값이지 기기에서 잰 값이 아니다. **개발 빌드가 나오면 다시 잰다.**

### 깨진 것 둘 — 둘 다 `ListRow` 다

**금액이 화면 밖으로 나간다.** 시스템 글꼴 2.2배부터 `지급 합계 / 12,345,678원` 이
줄 밖으로 나갔다. `3,847,200원` 에는 끊을 자리가 없어서 — 숫자와 `원` 사이는 줄바꿈
자리가 아니다 — 값을 아무리 좁혀도 제 폭 아래로 못 줄고 그대로 잘린다.
**급여명세서에서 잘리는 것이 금액이다.**

| 375px | 넘친 줄 (실제 문구 22줄 기준) |
|---|---|
| ~1.95배 | 0 |
| 2.35배 | **5** |
| 2.95배 | **12** |
| 3.12배 | **13** |

**`right`가 붙는 줄은 1.95배부터 깨진다.** 주 52시간 줄(`9.1 ~ 9.7` + `52시간이
코앞이에요`)과 연차 신청 목록 줄이다. 라벨이 길고 오른쪽에 두 줄짜리 덩어리가 서는
자리라 더 빨리 넘친다 — 1.95배에서 44px·30px 밖으로 나갔다.

### 고친 것 — 값이 아랫줄로 내려간다

`ListRow`의 `justifyContent: 'space-between'`을 빼고 **`flexWrap: 'wrap'` + 값에
`flexGrow`**를 줬다. 관리팀 연차 달력에서 이름을 지키려고 쓴 처방과 같다.

- 한 줄에 들어갈 때는 값이 남는 폭을 먹고 오른쪽 끝에 선다 — **1.35배까지 높이도 위치도 같다**
- 넘칠 때만 값이 아랫줄로 내려가 **온전한 금액이 남는다**
- 라벨에도 `flexShrink`를 줬다. 라벨은 끊을 자리가 있어서 접힌다

**3.12배까지 넘치는 줄이 0이 됐다** (375·360·320px 세 폭 모두). `right` 줄도 같다 —
1.95배 44px·30px 넘침이 0이 됐고, 1.64배에서 349px까지 늘어나던 연차 신청 줄이 118px 이 됐다.

### 안 깨졌지만 고친 것 — 버튼의 고정 높이

`Button`이 `height: 54`·`height: 44`로 **높이를 고정하고 있었다.** `DESIGN_RULES.md`
4·7장과 `spacing.rowHeight` 주석이 둘 다 "고정 높이로 쓰지 않는다"고 적고 있다.

**오늘은 안 잘린다.** 라벨에 `maxFontSizeMultiplier` 1.4가 걸려 있어 글자가 29px에서
멈추고 54·44 안에 한 줄로 들어간다. 상한을 뺀 채로 재보면 `이전 달 보기`가 **2배에서
두 줄이 되어 44 안에서 잘렸다.** 상한을 올리거나 라벨이 한 글자만 길어져도 같은 일이 난다.

`minHeight`로 바꿨다. **상하 여백은 주지 않았다** — 8을 주면 1.35배에서 버튼이 44에서
45로 자란다. 안 깨지는 자리를 건드리지 않는다.

### 안 고친 것

- **320px 에서 달력 칸이 38.8×50 이다.** 최소 터치 44×44에 못 미친다. 375에서 46.7×50,
  360에서 44.6×50으로 통과하고, **320은 명세가 잡은 지원 폭(375×667) 밖이라 그대로 뒀다**
- 하단 CTA는 다섯 화면 모두 `useSafeAreaInsets` + `KeyboardAvoidingView`로 이미 받고 있다
- `TextField`·`Sheet`·`Calendar`는 이미 `minHeight`와 배율 상한을 쓰고 있어 손댈 것이 없었다

### 곁다리로 본 것

`Gauge` 컴포넌트를 **아무 화면도 쓰지 않는다.** 52시간을 게이지로 그리려다 서버가
비율을 주지 않아 접은 자리다 (`app/attendance/index.tsx` 주석). 지우지 않고 남겨 뒀다.
