# 연차 API 명세

Swagger `6. 연차` 태그를 옮긴 것이다. 원본이 항상 우선한다.

| | |
|---|---|
| 출처 | `https://api.dvi-ind.com/hi-yo/v3/api-docs` (Swagger UI `/hi-yo/swagger-ui/index.html`) |
| API 버전 | `DVI 인사시스템 API` v1 |
| 확인일 | 2026-08-27 (단체연차·공휴일은 2026-08-28) |
| 서버 | `https://api.dvi-ind.com/hi-yo` (개발) |

**잔여 · 대장 · 달력 · 발생 입력**이다. 같은 모듈인 **단체연차(8장)·공휴일(9장)**도 여기 담았다 —
태그는 다르지만 연차 차감에 직접 걸린다. 신청과 결재는 `docs/API_신청결재.md`에 있다.

> **연차 발생은 자동으로 생기지 않는다.** 관리팀이 손으로 넣는다.
> 스펙이 이유를 적어두었다 — **입사 첫 해 규칙이 확정되지 않아 자동화하면 틀린 값이
> 조용히 쌓인다.** `CLAUDE.md` 3장이 "연차 발생·소멸 기준"을 추측 금지 항목으로 둔 것과 같은 이야기다.
> 앱은 발생일수를 만들어내지 않는다.

> **확인일 기준 연차 데이터가 전부 0이다.** 발생 0건, 대장 38명 전원 `noGrant`,
> 잔여 전부 0, 달력 0건. 화면을 붙이면 빈 상태부터 만난다.

> **공휴일이 9건뿐이고 설날·추석이 없다.** 음력 공휴일과 대체공휴일이 등록돼 있지 않다.
> 연차 차감은 공휴일을 세지 않는데 서버가 아는 공휴일이 이게 전부라, 지금 상태로 설 연휴에
> 연차를 신청하면 **연휴가 연차에서 깎인다.** 9장에 목록이 있다.

## 1. 공통

### 인증 · CORS

급여와 같다. `docs/API_급여.md` 1장을 본다.

### 응답 형식

**목록이 배열로 온다. 봉투가 아니다.** 신청·결재(`content`/`totalElements`)와 다르고
급여와 같다.

- 페이지네이션이 없다. **연차관리대장은 전 직원이 한 번에 온다** (확인일 기준 38명)
- 날짜에 타임존이 붙지 않는다. 서버는 한국 시간으로 돈다
- 일수는 소수를 쓴다 (`0.5`, `0.25`). 표기는 `@hr/format`의 `formatLeaveDays`를 거친다

### 오류

급여·신청결재와 같은 모양이다. `message`는 **사용자에게 그대로 보여줘도 되는 한국어**다.

`422`는 값 오류가 아니라 **업무 규칙 위반**이다. 이 태그에서 확실한 예가 둘 있다 —
발생 **수정·삭제로 잔여가 음수가 되는 경우**다 (3장).

> 오류 응답이 스펙에 선언돼 있지 않다. 9개 엔드포인트 전부 200만 문서화돼 있다.

## 잔여는 어느 값인가 (2026-08-31 확정)

**화면의 "남은 연차"는 `remaining`이다.** 서버 답변 —

> 결재 대기중인 신청까지 빼야 중복 신청을 막습니다. `confirmedRemaining`은 "실제로 소진된
> 기준"이라, 직원이 왜 잔여가 줄었지 하고 볼 때 함께 보여주려고 나눠 둔 값입니다.

- **신청을 막는 판단에는 `remaining`을 쓴다.** 이미 낸 신청이 결재를 기다리는 동안에도
  그만큼은 없는 것으로 본다
- `confirmedRemaining`은 보조로 같이 보여줄 수 있는 값이다. 둘의 차이가 곧 "결재 대기중"이다
- **이 확정으로 S-301의 잔여 표시가 풀렸다.** 그전까지는 어느 값인지 몰라 숫자를 아예 띄우지
  않고 있었다

서버 스펙(`LeaveBalanceResponse` 주석)에는 적혀 있는데 Swagger로 나오지 않았다고 한다.
스키마 설명에 나오도록 고치겠다는 답을 받았다.

## 2. 잔여는 어떻게 만들어지는가

```
발생(grant)  ─┐
              ├─→  잔여(remaining)
사용·대기    ─┘
POST /requests (신청·결재 태그)
```

- **발생**은 관리팀이 `POST /leave/grants`로 넣는다. 자동 부여가 없다
- **사용·대기**는 신청·결재에서 온다. 승인된 것이 `used`, 대기중인 것이 `pending`
- **잔여는 서버가 계산한다.** `granted - used - pending`을 앱에서 하지 않는다

같은 직원·같은 연도에 발생을 **여러 건** 넣을 수 있다. 정기 발생과 별도 부여를
나눠 기록하기 위해서다.

### LeaveBalanceResponse

| 필드 | 타입 | 설명 |
|---|---|---|
| `employeeId` | int64 | |

**`remaining`과 `confirmedRemaining`을 서버가 둘 다 준다.** 둘의 차이가 무엇인지는
스펙에 설명이 없다 (7장 2번). **어느 쪽을 화면에 쓸지 정해지기 전까지 잔여를 표시하지 않는다.**
둘을 앱에서 빼거나 더해 만들어내지 않는다.

### LeaveGrantCreateRequest

| 필드 | 타입 | 필수 | 설명 |
|---|---|---|---|
| `employeeId` | int64 | ✅ | |
| `fiscalYear` | int32 | ✅ | |
| `grantType` | enum | ✅ | 5장 |
| `grantedDays` | number | ✅ | |
| `grantedOn` | date | | 발생일 |

있다 (2026-09-01 스웨거 재확인). **이월이 없기 때문**이라는 근거까지 붙어 있다.
등록 화면에서 소멸일을 비워도 되고, 화면이 12월 31일을 만들어 넣지 않는다.

`LeaveGrantCreateRequest`의 필드에 `id`, `employeeName`, `createdByName`이 붙는다.

**`createdByName`이 "누가 넣었나"에 답한다.** 발생 일수 분쟁에 필요한 값이다.

## 5. 발생 종류 (`grantType`)

| 코드 | 스펙의 설명 |
|---|---|
| `MONTHLY` | 없음 |
| `REGULAR` | 없음 |
| `SENIORITY` | 없음 |
| `NEW_HIRE` | 없음 |
| `CARRY_DEDUCT` | 없음 |

**다섯 개 모두 설명이 없다.** 이름에서 뜻을 짐작할 수는 있으나 확정된 근거가 아니다.
특히 `CARRY_DEDUCT`(이월인지 차감인지, 둘 다인지)가 모호하다.

**등록 화면에서 종류를 고르게 하려면 각각이 무엇인지 정해져야 한다.** 잘못 고르면
발생 일수가 틀리게 쌓인다. 7장 4번.

## 6. 앱 관점 정리

### S-301 연차 현황 및 신청 (`apps/mobile`)

| 단계 | 호출 |
|---|---|
| 잔여 | `GET /leave/balance` |
| 달력 | `GET /leave/calendar?from=&to=` |
| 신청 | `docs/API_신청결재.md` |

- 잔여를 앱에서 계산하지 않는다. `granted - used - pending`을 쓰지 않는다
- **`remaining`과 `confirmedRemaining` 중 무엇을 보여줄지 정해지기 전까지 숫자를 띄우지 않는다**
- 달력은 `from`·`to`가 필수다. 화면이 보는 범위를 그대로 넣는다
- **본인 것만 부른다.** `/leave/calendar/all`과 `/leave/ledger`를 `apps/mobile`에 넣지 않는다

### 관리팀 화면 (`apps/admin`)

| 화면 | 호출 |
|---|---|
| 연차관리대장 | `GET /leave/ledger?year=` |
| 발생 등록·수정·삭제 | `POST` / `PUT` / `DELETE /leave/grants` |
| 전 직원 달력 | `GET /leave/calendar/all?from=&to=` |

- 대장은 전 직원이 한 번에 온다. 표 정렬은 **서버가 지원하는 열에만** 넣는다 (지금은 없다)
- **`noGrant`를 반드시 구분해 보여준다.** 발생 누락을 발견하는 것이 이 대장의 목적이다
- 발생 삭제·수정은 잔여가 음수가 되면 서버가 막는다. 그 `message`를 그대로 보여준다

**대장은 만들었다** (A-303, `apps/admin` `/leave-ledger`, 2026-09-01).
**전 직원 달력도 만들었다** (A-301, `apps/admin` `/leave-calendar`, 2026-09-01).
**발생 등록·수정·삭제(A-306)는 만들지 않았다** — 7장 1번과 4번에 걸린다.

달력에서 정한 것 —

- **`from`·`to`에 격자의 처음과 끝을 넘긴다.** 그 달의 1일~말일이 아니다. 달력 격자는
  앞뒤 달 날짜까지 덮으므로, 1일~말일만 부르면 첫 줄과 마지막 줄에 걸친 날이 비어 보인다
- **칸에 건수가 아니라 이름을 적는다.** 셋이 쉬는 날에 `3건`이라고만 적으면 그 셋이
  같은 팀인지 알 수 없다. 종류는 `typeName`을 그대로 옆에 둔다
- **공휴일(`GET /holidays`)을 같이 깐다.** 아무도 안 쉬는 날이 공휴일이라서인지
  그냥 빈 날인지 구분이 안 되면 달력을 잘못 읽는다

| 8 | **페이지네이션 없음** | 대장이 전 직원을 한 번에 준다. 지금은 38명이지만 늘면 대응이 필요하다 |

| 10 | ~~단체연차 부족분 처리~~ | **풀렸다 (2026-09-01 인사팀). 명단만 받고 개별 처리한다** — 지금 서버 동작이 맞다. 자동 무급 전환이 아니다. **틀린 것은 명세서 5장 예외 2번**이고, 서버가 고치기로 했던 항목이라 이 답을 넘겨야 한다 |
| 11 | **A-301 화면 상세 스펙** | 연차관리대장·달력·발생 등록 화면의 필드·정렬·버튼 동작이 정의돼 있지 않다. 대장과 달력은 스키마의 열이 곧 화면의 열이라 명세서 3장의 준용 규칙으로 만들었다 (A-504·A-503과 같은 기준). 발생 등록은 준용으로 메울 수 없다 — 4번이 값의 문제이지 배치의 문제가 아니다 |

**이제 4번 하나가 발생 등록 화면(A-306)을 막고 있다.** 몇 일을 넣는지는 정해졌고,
종류를 고르는 칸에 넣을 다섯 개의 뜻만 남았다.

### `grantType`을 이렇게 물어본다 (2026-09-01)

"다섯 개가 무슨 뜻인가요"보다 좁게 물을 수 있게 됐다. **우리 규칙이 확정됐으니**
넣을 종류가 몇 가지인지가 정해지고, 남는 것을 콕 집어 물으면 된다.

> 저희는 **입사일 기준 · 근로기준법 그대로**입니다. 그러면 넣는 것이 셋인데요 —
> 1년 미만 월 단위 발생은 `MONTHLY`, 1년차부터의 15일은 `REGULAR`,
> 3년차부터의 근속가산은 `SENIORITY`가 맞나요?
> 그리고 **`NEW_HIRE`는 `MONTHLY`와 무엇이 다른가요?** 화면 인벤토리의 A-306이
> "신입휴가 수동 입력"이라 어느 쪽을 쓰는지가 갈립니다.
> **이월이 없다고 하셨는데 `CARRY_DEDUCT`는 언제 쓰나요?**

**답을 받기 전에는 짝지어 쓰지 않는다.** 이름이 그럴듯하다는 것은 근거가 아니다
(`CLAUDE.md` 3장).

2번(잔여 정의)은 풀려서 S-301의 잔여 표시가 나왔고, **조회만 하는 대장(A-303)은
막혀 있지 않아 만들었다** — 대장은 종류를 고르지 않고 서버가 준 숫자를 표기만 한다.

## 8. 단체연차 (`7. 단체연차`)

여름휴가처럼 **전 직원이 같은 날 쉬는 일정**이다. A-304가 쓴다 —
화면을 만들었다 (`apps/admin` `/company-leaves`, 2026-08-31).

| 메서드 | 경로 | 용도 |
|---|---|---|
| GET | `/company-leaves` | 등록된 목록. `year` 선택 |
| POST | `/company-leaves` | 날짜 등록. **아직 차감되지 않는다** |
| POST | `/company-leaves/{id}/apply` | **일괄 차감 실행. 한 번만 할 수 있다** |

**Swagger에 `관리팀만` 표시가 없지만 서버는 막고 있다.** 일반 직원(`employee:90`)이
`GET /company-leaves`를 부르면 `403`이다 (2026-08-31 실호출). 표시가 빠진 것으로 보인다 —
당직 명단 조회와 같은 종류의 누락이다. 서버에 알려 스펙을 맞춰야 한다.

**지우는 API가 없다.** `GET`·`POST`·`apply` 셋뿐이라 잘못 등록한 날짜를 되돌릴 수 없다.
공휴일에는 `DELETE`가 있는 것과 다르다. 화면에 삭제 버튼을 만들지 않았고, 그래서
등록 대화상자가 요일을 같이 보여준다.

**의도가 아니라 빠진 것이라는 답을 받았다** (2026-08-31). **적용 전만 지울 수 있게** 열겠다고
한다 — `apply`를 눌러 전 직원 연차가 깎인 뒤에 날짜를 지우면 차감이 되돌아가지 않아
숫자가 어긋나기 때문이다. 열리면 `applied === false`인 행에만 삭제를 붙인다.

**등록과 차감이 나뉘어 있다.** 등록만으로는 아무 일도 일어나지 않고, `apply`를 눌러야
실제로 신청서가 만들어진다. 되돌릴 수 없는 동작이라 화면은 확인 단계를 거쳐야 한다.

### `CompanyLeaveResponse`

`id` `targetDate` `reason` `applied` `appliedAt` `appliedByName`

`applied`가 이미 차감했는지다. 누가 언제 눌렀는지가 남는다.

### `CompanyLeaveCreateRequest`

필수 `targetDate` `reason`

### `CompanyLeaveApplyResponse`

`companyLeaveId` `targetDate` `reason` `deductedCount` `skippedCount`
`insufficient[]` `alreadyOnLeave[]` `notice`

> **핵심은 `insufficient`다.** 스펙이 직접 적고 있다 —
> "잔여가 모자란 직원은 차감하지 않고 명단으로 돌려줍니다. **무급 전환이나 마이너스 처리는
> 시스템이 정할 문제가 아닙니다** — 관리팀이 사람별로 판단해야 합니다."

`SkippedEmployee { employeeId, employeeNo, employeeName, departmentName, remaining, reason }`

급여 계산의 `skipped`와 같은 구조다. **성공 개수만 보여주면 안 된다** —
`DESIGN_ADMIN.md` 3장이 요구하는 대로 명단을 도구줄에 따로 보여준다.

> **명세서와 어긋난다.** 명세서 5장 예외 2번은 "잔여분까지는 연차 차감, 부족분은 무급
> 처리로 자동 전환"이라고 적고 있는데 **서버는 자동 전환을 하지 않는다.**
>
> **화면은 지금처럼 명단만 보여주는 쪽으로 둔다** (2026-08-31 서버 답변).
> 명세서는 서버 쪽이 인사팀에 확인해 고치기로 했다 — 프런트가 넘길 것은 없다.

## 9. 공휴일 (`8. 공휴일`)

**연차 차감일 계산에서 이 날짜들이 빠진다.** 관리팀 화면을 만들었다 — `apps/admin` `/holidays`
(2026-08-31. `docs/00_문서_인덱스.md` 「공휴일 관리」).

|---|---|---|---|
| GET | `/holidays` | — | 목록. `year` 선택 — **비우면 전체가 아니다** (아래) |

| DELETE | `/holidays/{id}` | **관리팀** | 삭제 |

- **넣는 즉시 이후 연차 계산에 반영된다**
- **지우면 이미 그 날짜로 계산된 연차는 다시 계산되지 않는다.**
  잘못 등록한 것을 바로 지우는 용도다

`HolidayResponse` / `HolidayCreateRequest` — `holidayDate` `name` `holidayType` (등록은 셋 다 필수)

`holidayType`은 **enum 두 값이다 — `PUBLIC` · `COMPANY`** (2026-08-31 Swagger 확인).
`POST`의 설명이 "회사 지정 휴무일도 여기에 넣는다"라고 적고 있어 `COMPANY`가 그것이다.
2026-08-27자 초안에 "어떤 값이 들어가는지 스펙에 없다"고 적었던 것은 풀렸다.

TODO: **구분에 따라 연차 차감이 달라지는지는 여전히 모른다.** 목록은 두 값을 섞어서 주고,
차감 계산이 `holidayType`을 보는지 아닌지가 스펙에 없다. 회사 지정 휴무일을 넣기 전에 확인한다.

### `year`를 비우면 전체가 오지 않는다 (2026-08-31 확인)

Swagger는 `year`를 선택 파라미터로만 적고 있어 비우면 전체로 읽힌다. **아니다.**

| 요청 | 결과 |
|---|---|
| `GET /holidays` | **9건 — 2026년만** (`id` 1~9) |
| `GET /holidays?year=2026` | 9건 (`id` 1~9) |
| `GET /holidays?year=2027` | **9건 — 2027년** (`id` 10~18) |
| `GET /holidays?year=2025` · `2028` | `[]` |

**시드에 2027년도 들어 있다.** 2026-08-27자로 "9건뿐"이라고 적었던 것은 올해만 본 것이고,
실제로는 18건이다. 두 해 다 같은 양력 고정일 9개다.

**올해가 기본값이다** (2026-08-31 서버 답변). 오름차순 첫 해가 아니라 현재 연도다.
의도된 동작이다.

**등록된 연도를 알아내는 경로는 없다.** 보험 요율의 `/years` 같은 것을 공휴일에도 열 수
있다고 했다 — 필요해지면 요청한다. 지금은 화면이 올해·내년만 고르게 두었다
(`apps/admin/src/features/holidays/api.ts` `selectableYears`).

### 공휴일은 지금 빠져 있다 (2026-08-27 확인, 2026-08-28·31 재확인 — 그대로다)

`GET /holidays?year=2026`이 **9건**을 준다. 전부 `holidayType`이 `PUBLIC`인 양력 고정일이다.
2027년도 같은 9건이다.

```
01-01 신정      03-01 삼일절    05-01 근로자의 날
05-05 어린이날  06-06 현충일    08-15 광복절
10-03 개천절    10-09 한글날    12-25 성탄절
```

**설날 · 추석 · 부처님오신날이 없다.** 음력이라 시드에 들어가지 않았다.
**대체공휴일도 없다.**

연차 차감은 주말·공휴일을 세지 않는데(`docs/API_신청결재.md` 1장), 서버가 아는 공휴일이

연차 화면보다 이 입력이 먼저다.

## 10. 연차촉진 — 종이 서식에서 확정됐다 (2026-09-02)

**API가 아직 없다.** 63개 경로에 촉진·계획서가 하나도 없다 (7장). 여기 적는 것은
**회사가 쓰는 두 서식**에서 읽은 규칙이다 — 서버가 조건을 정할 때 이 값을 쓴다.

받은 것은 엑셀 두 시트다 — 「연차사용촉구서(1차)」와 「연차사용계획서 [1차]」.
**원본은 리포에 넣지 않았다.** 실명과 실제 근태가 들어 있다 (`CLAUDE.md` 2장).

### 언제 보내는가

시트의 셀 메모에 적혀 있던 값이다.

| 차수 | 시점 |
|---|---|
| **1차 통보** | **연차 소멸 6개월 전** |
| **2차 통보** | **연차 소멸 2개월 전** |

소멸이 그해 12월 31일이므로(이월 없음, 2026-09-01 확정) **1차는 7월 초, 2차는 11월 초**가
된다. 사람마다 도는 것이 아니라 **연 단위로 한 번** 돈다 — 인사팀이 준 「기준일 1월 1일」과
맞는다.

### 1차 — 연차사용촉구서

> 상기인은 향후 2개월간 연차휴가 사용 시기를 정하여 **10일 이내에 회사로 통보**해 주시기
> 바랍니다. 통보하지 않으면 회사가 **연차휴가 사용기간 마지막 두 달 사이의 일자를 임의로
> 지정**하여 **사용기간 종료일 2개월 전까지 통보**합니다. 지정한 날에도 쓰지 않으면
> **소멸하며 수당도 지급되지 않습니다.**

서식에 있는 칸이다.

| 칸 | 값 |
|---|---|
| 성명 · 부서명 · 직책 · 입사일 | 직원 정보 |
| 연차휴가 발생시점 | **입사일** |
| 연차휴가 발생일수 · 특별휴가 발생일수 · **총 연차휴가 발생일수** | 셋을 따로 적는다 |
| 연차휴가 사용기간 | 오늘 ~ **그해 12월 31일** |
| 사용한 연차 일수 | **기준일 1월 1일 ~ 오늘** |
| 잔여 연차 일수 | |

**표기는 연차 1 · 반차 0.5다.** 서식에 그렇게 적혀 있다.

### 2차 — 연차사용계획서 (S-302가 이것이다)

근로기준법 제61조를 근거로 적고 있다. **10일 이내 제출**이다.

| 칸 | 값 |
|---|---|
| 성명 · 부서명 · 직책 · 입사일 | |
| 총 연차휴가 발생일수 · 사용한 연차 일수 · 잔여연차일수 | 촉구서와 같은 값 |
| **사용계획일수** | 직원이 적는다 |
| 달력 | **연차는 빨간 동그라미, 반차는 세모.** 음영은 휴무일(공휴일 등) |
| **제출자 : ______ (서명 또는 인)** | **서명란이 여기 있다** |

- **변경은 3일 전**에 담당자를 통한다. 기재한 연차사용일은 **그 월에 모두 사용**해야 한다
- 서식에 메모가 붙어 있다 — **「날짜 선택할 수 있는 달력 필요!」**, 「달력 있으면 ② 삭제」.
  종이의 ②는 「음영은 휴무일」 안내다. **화면에서는 달력으로 고르게 하고 그 줄을 뺀다**는 뜻이다

### 그래서 서버에 필요한 것

조건은 이제 다 있다. **없는 것은 API뿐이다.**

| 무엇 | 왜 |
|---|---|
| 촉진 대상·차수 조회 | 누구에게 몇 차를 보냈는지 |
| 계획서 제출 (`POST`) | 사용계획일수와 **날짜 목록**, 그리고 **서명** |
| 회사 지정일 통보 | 2차에서 회사가 정한 날 |

**서명이 필요한 곳이 하나 더 늘었다.** 계획서에 「제출자 (서명 또는 인)」이 있는데,
지금 `signatureImage`는 결재(`RequestDecisionRequest`)에만 있다
(`API_신청결재.md` 7장 10번과 같은 문제다).
