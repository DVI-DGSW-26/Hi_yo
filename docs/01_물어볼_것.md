## 0. 인증 — 거의 풀렸다 (2026-09-01 서버 답)

서버가 「HRM 로그인 붙이기」로 답을 줬고, **우리가 물어본 다섯 중 넷이 없어졌다.**

**방식이 우리가 생각한 것과 달랐다.** 프런트가 Keycloak과 직접 말하는 것이 아니라
**서버가 로그인을 중계하고 프런트에는 토큰만 넘긴다.** 그래서 —

| 물어봤던 것 | 답 |
|---|---|
| 프런트용 public client 등록 | **필요 없다.** 서버가 Keycloak과 직접 로그인한다. PKCE도 OIDC 라이브러리도 필요 없다 |
| 관리팀 콜백 등록 | **이미 돼 있다.** `/auth/callback`을 `localhost` 5173·3000과 `127.0.0.1` 네 조합으로 열어 뒀다 |
| 커스텀 스킴 리다이렉트가 되는지 | **된다. 등록만 하면 된다** — 아래 남은 것 참고 |
| 테스트 계정 Keycloak 아이디 | 우리가 가입하고 알려주면 된다 — 아래 남은 것 참고 |

**우리 코드는 거의 맞아 있었다.** fragment(`#token=`)로 받는 것, `sessionStorage`에 두고
`localStorage`를 피하는 것, `Authorization: Bearer`, `/auth/me`로 권한을 받는 것,
401 재이동을 한 번으로 막는 것까지 전부 서버 안내와 같다.

**고친 것은 둘이다** (2026-09-01).

- 로그인 입구를 `oauth2/authorization/keycloak` → **`/auth/login`**으로 바꿨다.
  둘 다 살아 있지만 `redirect`를 받는 쪽은 `/auth/login`뿐이다
- **모바일이 `redirect`를 안 싣고 있었다.** `callbackUrl()`을 만들어 두고 `loginUrl()`에
  붙이지 않아서, 등록이 끝나도 **토큰이 앱으로 오지 않을 코드였다.** 진짜 버그였다

### 실제로 끝까지 돌려봤다 (2026-09-01)

**앱 쪽 배선은 확인됐다.** 로그인 버튼 → Keycloak 로그인 → OTP → 서버가
`localhost:5173/auth/callback` 으로 정확히 돌려보내는 데까지 실제로 통과했다.

거기서 **토큰 대신 `#error=` 가 왔다.** 화면에 뜬 문구는 우리가 만든 것이 아니라
서버가 보낸 값을 그대로 보여준 것이다 — `로그인하지 못했습니다. 관리자에게 문의하세요.`

| 단계 | 결과 |
|---|---|
| 회원가입 · 비밀번호 | **통과** |
| OTP 등록 (Keycloak이 필수로 걸어 뒀다) | **통과** |
| 콜백 도달 (`#error=` 를 우리 화면이 받아 그림) | **통과** |
| 그룹 배정 · 인사 정보 연결 | **여기서 막혔다** |

**어느 쪽인지는 응답으로 구분되지 않는다.** 서버 문서가 그렇게 적고 있고 이유는 서버
로그에만 남는다 — 아이디를 알려주면 서버가 어디서 끊겼는지 봐 준다.

**OTP 등록이 필수라는 것은 문서에 없던 것이다.** 뒤에 가입할 사람도 같은 화면을 만난다.
앱 항목이 여러 개 쌓이면 옛 코드를 넣게 되므로, 다시 등록할 때는 인증기 앱의 옛 항목을
지우고 새 QR로 받는다.

### 그 뒤 — 로그인이 열렸다 (2026-09-03)

**그룹 배정이 풀려 관리팀 웹으로 로그인이 된다.** `sehuii`로 토큰을 받아 `/auth/me`가
통했고 직원 46명이 실제 값으로 떴다. 9-01에 `#error=`로 막히던 자리가 지나갔다.
자세한 것은 `00_문서_인덱스.md` 「로그인이 열렸다」에 있다.

### 콜백 주소가 등록됐다 (2026-09-04)

**0.3이 해소됐다.** 서버가 `hr://auth/callback`을 등록했고 부딪혀 확인했다.

| 부른 주소 | 응답 |
|---|---|
| `hr://auth/callback` | **302** → `/oauth2/authorization/keycloak` |
| `hr://auth/nope` (대조군) | `400 등록되지 않은 콜백 주소입니다` |

대조군을 같이 부른 것은 **검증이 꺼진 것이 아니라 우리 주소만 추가된 것**인지 보기
위해서다. 엉뚱한 주소는 여전히 400이다.

**확인된 것은 입구뿐이다.** 로그인을 통과한 뒤 서버가 실제로
`hr://auth/callback#token=<JWT>`로 돌려보내는지는 **앱이 기기에 있어야** 볼 수 있다.
커스텀 스킴이라 PC 브라우저로는 끝까지 가지 못한다.

### 앱이 슬래시 3개를 보내고 있었다 (2026-09-08) — 고쳤다

**등록은 맞았는데 앱이 다른 주소를 보내고 있었다.** 배포 APK를 안드로이드 실기기에
올려 로그인을 눌렀더니 서버가 이렇게 답했다.

```
등록되지 않은 콜백 주소입니다. 백엔드에 이 주소를 알려주세요: hr:///auth/callback
```

`expo-linking`의 `createURL`이 마지막을 `scheme + ':' + '/' + hostUri + path`로 조립하는데,
커스텀 스킴 배포 빌드는 `hostUri`가 비어서 `ensureLeadingSlash('', true)`가 `/`를 돌려주고
거기에 경로의 앞 슬래시가 또 붙는다. **개발 빌드에서는 `hostUri`가 `192.168.x.x:8081`이라
드러나지 않는다** — 브라우저로도 개발 빌드로도 못 잡고, **배포 APK를 실기기에 올려야
보이는 버그였다.** 이 확인을 한 이유 그대로다.

경로에서 앞 슬래시를 뺐다 (`src/lib/auth.ts`, PR #119). 개발 빌드는 그대로다.

**지금은 둘 다 등록돼 있다** (2026-09-08 실호출 확인).

| 부른 주소 | 응답 |
|---|---|
| `hr://auth/callback` (고친 앱이 보내는 것) | **302** |
| `hr:///auth/callback` (지금 퍼진 APK가 보내는 것) | **302** |
| `hr://auth/nope` (대조군) | `400 등록되지 않은 콜백 주소입니다` |

**서버에 더 요청할 것은 없다.** 남은 것은 새 APK로 로그인이 끝까지 가는지 보는 것뿐이다.

### 갱신·로그아웃이 생겼다 (2026-09-08 서버 답)

**토큰 수명이 5분에서 15분이 됐고, 갱신과 로그아웃 경로가 열렸다.** 명세에도 올라와 있다.

| 무엇 | 규칙 |
|---|---|
| `GET /auth/refresh` | **세션 쿠키로 인증한다** — `credentials: include` 필수, **`Authorization` 헤더를 붙이지 않는다**(만료된 토큰으로는 신원을 증명할 수 없다). 200 `{token, expiresIn}` · 401 이면 재로그인. **만료 1분 전에 미리 부른다** |
| `POST /auth/logout` | 서버 세션만 끊는다. **이미 발급된 토큰은 JWT 라 거둬들일 수 없다 — 프런트가 지워야 로그아웃이 완성된다.** 이미 로그아웃 상태여도 200. **Keycloak 세션은 안 끊긴다** |
| 수명 15분 | **`expiresIn` 을 쓰고 15분을 코드에 적지 않는다.** Keycloak 설정이라 또 바뀔 수 있다 |
| 401 | **정상 경로다.** 서버가 인증 정보를 메모리에 들고 있어 **배포할 때마다 날아간다** — 배포 직후 `refresh` 는 401 이다. 오류 화면이 아니라 재로그인으로 이어져야 한다 |

**쿠키가 `SameSite=Lax` 라 프런트와 API 가 같은 사이트(`*.dvi-ind.com`)여야 실린다.**
개발은 `localhost` 라 다른 사이트여서 **쿠키가 실리지 않는다** — 개발 중 갱신 401 은 정상이고,
실제로 도는지는 **배포 주소가 정해져야** 확인된다. 다른 도메인에 올릴 거면 서버에 알려야 한다
(쿠키 설정을 바꿔야 한다고 했다).

**관리팀 웹에 붙였다** (2026-09-09) — 만료 1분 전 갱신, 로그아웃에서 서버 세션까지 끊기.
갱신이 실패해도 로그아웃시키지 않는다. 지금 토큰은 아직 살아 있고, 실제로 죽는 순간 401 이
와서 기존 재로그인 경로가 받는다. **쿠키가 안 실리는 개발 환경에서 튕기지 않게 하려는 것도 있다.**

#### 콜백 주소 — 슬래시 3개짜리가 제거됐다

| 주소 | |
|---|---|
| `hr://auth/callback` | **✅ 앱용** (슬래시 2개) |
| `hr:///auth/callback` | **❌ 제거됐다** |

**그래서 PR #119 이전 APK 는 이제 로그인이 400 이다.** 실기기 확인은 `9c83030a` 이후 빌드로만
된다. 웹 배포 주소가 정해지면 미리 알려야 등록된다 — 슬래시 하나만 달라도 400 이고
서버가 느슨하게 받아주지 않는다(등록 안 된 주소로 토큰이 나가는 것을 막으려고).

#### 모바일은 방식이 뒤집혔다 — 답 셋이 더 필요하다

서버 안내: **앱은 `/auth/login` 을 거치지 않고 Keycloak 과 직접 OIDC + PKCE 로 붙는다**
(RFC 8252). 앱이 리프레시 토큰을 직접 들고 조용히 갱신해 브라우저가 반복해서 뜨지 않는다.
`react-native-app-auth` 를 권했고, `/auth/refresh`·`/auth/logout` 은 **웹 전용**이라고 했다.

**2026-09-01 답(「프런트용 public client 도 PKCE 도 필요 없다, 서버가 중계한다」)이 뒤집힌 것이다.**
지금 앱은 서버 중계 방식으로 만들어져 있고 9-08에 실기기에서 토큰을 받아 `/auth/me` 까지
통과했다. **전환에 필요한 것이 문서에 없어서 코드를 쓰지 않았다 — 30·31·32번이다.**

## 1. 서버 — 2026-09-02에 전부 답이 왔다

**22건 전부에 답을 받았다.** 회신 문서는 「기다리던 답」이다. 열여섯은 이미 배포됐고,
여덟은 코드를 열어 확인한 값으로 답이 왔다. 둘은 회사가 정해야 하고(3장 A·B),
둘은 우리 몫이다(0.1·0.2).

**아래는 요청 목록이 아니다.** 무엇이 열렸고 우리가 무엇을 해야 하는지의 목록이다.
다시 묻지 않는다.

**`API_*.md`는 아직 이 답들을 반영하지 않았다.** 이 문서의 규칙대로라면 API 문서를 먼저
고치고 여기서 줄을 지워야 하는데, 한 번에 22건이 와서 **먼저 여기에 다 적어 뒀다.**
API 문서 반영은 화면을 고치면서 같이 한다 — 특히 `API_신청결재.md` 7장은 결재가
2단계가 되면서 **틀린 내용이 됐다.**

### ★ 화면을 고쳐야 한다 — 결재가 2단계가 됐다

**회사 「휴가(근태)신청서」 결재란이 「작성 · 검토 · 승인」 세 칸이었다.** 작성은 신청인
자리이니 결재는 **검토와 승인 두 단계**다. 인사팀이 「원칙대로 가자」고 확정했다.

    POST /requests/{id}/review      ← 새로 생겼다
    POST /requests/{id}/decision

몸통은 둘 다 기존 `RequestDecisionRequest` 그대로다 — `approved` · `comment` ·
`signatureMethod` · `signatureImage`.

| status | 화면이 보여줄 것 |
|---|---|
| `PENDING` | **검토** 버튼 → `/review` |
| **`REVIEWED`** | **승인** 버튼 → `/decision`. 단 **내가 검토자면 비활성** |
| `APPROVED` · `REJECTED` · `CANCELED` | 결재 완료 |

**`REVIEWED`가 새로 생겼다.** status를 열거해 쓰는 곳을 빠짐없이 고친다 — 목록 필터 ·
뱃지 · 정렬 전부다.

**검토한 사람은 승인할 수 없다.** 같은 사람이 두 칸을 채우면 단계를 나눈 뜻이 없어
서버가 **422**로 막는다. 화면에서 미리 비활성으로 둔다 — 누르고 나서 거부당하게 두는
것은 화면의 잘못이다.

응답에 `reviewerId` · `reviewerName` · `reviewComment` · `reviewedAt` 넷이 늘었다.
기존 `approverId` 계열은 이제 **승인** 자리다.

이미 승인 · 반려된 신청은 **검토 칸이 비어 있다.** 실제로 검토한 사람이 없는데 이름을
넣으면 그것이 증빙으로 남아 소급해 채우지 않았다. 결재 대기 중이던 신청은 검토부터
다시 밟는다.

**9-01에 정리한 「2단계 결재가 없다」가 뒤집혔다.** 그때는 검토자·승인자가 독립 역할이
아니라 관리팀 내 지정이라고 정리했는데, 서식을 받고 나서 **단계 자체가 둘로 나뉘었다.**
`API_신청결재.md` 7장을 고쳐야 한다.

기준이 된다. 9-01에 인사팀에게 받은 값이 직무 마스터와 맞는지 확인해야 한다.
**필드는 바뀌지 않으니 화면은 먼저 만들어도 된다.**

**B. 연차 발생 기준이 두 갈래다.**

부여는 **입사일** 기준인데 잔여·소멸은 **회계연도**(1/1~12/31) 기준이다. 자동 부여를
켜려면 어느 쪽에 맞출지 정해야 한다. 그리고 **「매월 개근」을 무엇으로 판단할지**도
정해지지 않았다 — 결근 신청이 없으면 개근인지, 근태 기록까지 볼 것인지, 지각·조퇴가
개근을 깨는지.

**정해질 때까지 자동 부여는 꺼 둔 상태다.** 지금 켜면 46명의 연차가 틀린 기준으로 생긴다.
