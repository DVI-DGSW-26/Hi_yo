# 물어볼 것

**막혀 있는 것을 누가 풀어줘야 하는지의 목록이다.** 각 항목의 자세한 근거는
해당 API 문서에 있고 여기에는 **무엇이 막히는지**와 **무엇을 받아야 하는지**만 적는다.

답을 받으면 이 문서가 아니라 **해당 API 문서를 먼저 고치고**, 여기서는 줄을 지운다.
`00_문서_인덱스.md` 「앱 개발을 막고 있는 것」과 짝이다 — 그쪽이 우리 사정이고 이쪽이 요청이다.

마지막 정리 2026-09-01.

## 0. 지금 전부를 막고 있는 것

**프런트용 public client가 없어서 두 앱이 전 화면 `401`이다.** 2026-08-31 오전에 사내 OAuth가
켜진 뒤로 값이 찬 화면을 한 번도 못 봤다. 아래 목록의 절반은 "확인이 필요하다"인데,
**확인 자체가 이것 때문에 막혀 있다.**

관리팀 화면과 모바일 둘 다 로그인은 붙여 뒀다. 서버에 등록만 되면 바로 돈다.

| 받아야 하는 것 | 비고 |
|---|---|
| **프런트용 public client 등록** | `hi-yo`는 confidential이라 secret이 필요하고 redirect URI도 서버용이다 |
| **관리팀 콜백 등록** | `http://localhost:5173/auth/callback` |
| **모바일 콜백 등록** | 운영 `hr://auth/callback`. 개발 빌드 값은 기기에서 읽어 따로 넘긴다 |
| **커스텀 스킴 리다이렉트가 되는지** | 백엔드 안내가 웹 주소만 예로 든다. 안 되면 중간 웹 페이지를 한 번 거치는 방식으로 바꿔야 한다 |
| **테스트 계정의 Keycloak 아이디 연결** | 인사 정보에 연결돼야 `401`이 안 난다 |

우리가 줘야 하는 것 — **배포 주소**(CORS에 넣어준다. 관리팀·모바일이 다르면 둘 다). 아직 미정이다.

**5번은 이 문장 그대로 보내면 된다.**

> 저희는 **입사일 기준 · 근로기준법 그대로**입니다. 그러면 넣는 것이 셋인데요 —
> 1년 미만 월 단위 발생은 `MONTHLY`, 1년차부터의 15일은 `REGULAR`,
> 3년차부터의 근속가산은 `SENIORITY`가 맞나요?
> **`NEW_HIRE`는 `MONTHLY`와 무엇이 다른가요?** A-306이 "신입휴가 수동 입력"이라
> 어느 쪽을 쓰는지가 갈립니다.
> **이월이 없다고 하셨는데 `CARRY_DEDUCT`는 언제 쓰나요?**

**11번은 이렇다.** `GET /v3/api-docs`의 63개 경로에 **촉진·계획서가 하나도 없다**
(2026-09-01 확인). 계획서를 낼 경로도, 발송할 경로도, 서명을 붙일 자리도 없다 —
`signatureImage`는 `RequestDecisionRequest`(결재)에만 있다. 화면 인벤토리에는 S-302와
A-305가 올라 있는데 받쳐줄 API가 없는 상태다.

**조건도 서버가 정하기로 했다** (2026-09-01). 인사팀에서 들은 것은 둘이다.

| 들은 것 | |
|---|---|
| 촉진을 **1차·2차 두 번** 한다 | 화면이 둘로 나뉜다 — 계획서를 내는 쪽과 회사가 지정한 것을 보는 쪽 |
| 기준일이 **1월 1일**이다 | 사람마다가 아니라 **연 단위로 한 번** 돈다 |

**기준일이 1월 1일이라는 것이 `expiresOn`과 맞아떨어진다.** 발생은 입사일 기준인데
(인사팀 1번) 소멸은 비우면 **그해 12월 31일**이다 (서버 스펙, "이월이 없기 때문").
소멸이 연말이니 촉진도 연 단위로 도는 것이 앞뒤가 맞는다 — **촉진 배치가 사람마다
따로 돌 필요가 없다.**

**대상 잔여일수·발송 시점·응답 기한은 받지 못했다. 확정한 게 아니라 못 받은 값이니,**
**서버가 정할 때 인사팀과 맞춰야 한다.**

이름으로 id를 역매핑해야 하고, 이름이 겹치거나 부서명이 바뀌면 **엉뚱한 부서로 옮겨진다.**
`residentNo`가 분리돼도 `PUT`을 태우는 화면은 여전히 만들 수 없다.

## 3. 인사팀

| # | 무엇 | 막히는 것 |

| 1 | ~~연차 발생 규칙~~ | **풀렸다 (2026-09-01). 입사일 기준 · 근로기준법 그대로** — 1년 미만은 개근한 달마다 1일(최대 11일), 1년차부터 15일, 3년차부터 2년마다 +1일(최대 25일). A-306은 이제 서버 5번만 남았다 |
| 2 | ~~반차의 시작·종료 시각~~ | **풀렸다 (2026-09-01). 오전 `09:00~13:00` · 오후 `13:00~18:00`, 점심 포함.** S-301에 붙였다 |

**인사팀 몫이 다 끝났다 (2026-09-01).** 여섯 중 다섯은 답을 받았고, 연차촉진은
**서버로 넘어갔다** — 조건이 없어서가 아니라 API가 아예 없어서다 (서버 11번).

4·5·6은 지금 동작이 맞다는 답이라 고칠 것이 없었고, 1번은 값이 정해져 **A-306이 서버
5번 하나만 남았고**, 2번으로 **S-301 반차 신청을 붙였다.**

**남은 것은 아래 공휴일 입력 하나다.**

**특별휴가(경조사) 일수표는 받지 않아도 된다.** 특별휴가는 발생(grant)이 아니라 신청이고,
연차를 깎지 않는다 (`deductLeave` 없음). 며칠인지는 서버·인사팀이 판단할 값이라
**앱이 알 필요가 없다.**

### 급한 것 — 공휴일 입력

**확인이 아니라 입력이 필요한 항목이다.** 연차 차감이 서버의 공휴일 목록을 보기 때문에,
등록되지 않은 날은 근무일로 계산돼 **연휴가 연차에서 깎인다.**

2026-08-31에 설날·추석 6일을 넣었으나 그 뒤 시드가 다시 심어졌다. 인증이 풀리는 대로
`GET /holidays?year=2026`으로 **살아 있는지 먼저 확인하고**, 부처님오신날·대체공휴일이
빠져 있으면 같이 넣어야 한다. 음력과 대체공휴일 규칙은 문서에 없어 **화면이 대신
판정하지 않는다** — 사람이 달력을 보고 넣는다.
